# Revisión global del modelo de arquitectura — 1B2.8

Este documento consolida la revisión integral de las fases de diseño (1B2.1 – 1B2.7), validando la arquitectura propuesta contra la implementación actual en `main` y Supabase. Se han identificado cuatro contradicciones críticas que deben resolverse prioritariamente al iniciar la fase de implementación (1B.3).

## 1. Conclusiones de la Revisión
La arquitectura diseñada es robusta y coherente con las capacidades del sistema. Sin embargo, existen divergencias entre el diseño (fuente única de verdad) y la implementación actual (lógica duplicada y automatizaciones en base de datos).

## 2. Bloqueos críticos para 1B.3 (Contradicciones)
Antes de avanzar, 1B.3 debe resolver los siguientes conflictos:

### A. Autoridad de creación de proyectos (Proposal vs. Trigger)
- **Conflicto**: Un trigger actual (`sync_projects_from_accepted_request`) crea proyectos con `proposal_id = NULL` al aceptar una solicitud, contradiciendo el diseño de `proposals` (que exige una `proposal` validada).
- **Resolución**: La autoridad de creación debe migrarse al servicio `acceptProposal()`, deshabilitando o modificando el trigger actual.

### B. Mappings de estado divergentes
- **Conflicto**: Admin y Dashboard utilizan mappings de estados independientes para `project_requests` y proyectos.
- **Resolución**: Implementar una capa única de dominio con `ProjectStatus` y `RequestStatus` unificados, eliminando las traducciones locales en la UI.

### C. Fuentes de progreso fragmentadas
- **Conflicto**: Existen tres fuentes de progreso (Admin manual, Dashboard calculado, `production_stages` vacío).
- **Resolución**: Separar estrictamente `ProjectStatus` de `Progress`. Implementar `deriveEditorialJourney` como autoridad única para representar el progreso editorial real.

### D. Conexión de `EditorialJourney`
- **Conflicto**: La arquitectura de las 6 fases existe en diseño, pero el loader actual de Dashboard solo consulta un subconjunto de entidades.
- **Resolución**: Implementar el loader unificado que combine `project_requests`, `evaluations`, `proposals`, `projects` y `reviews` para derivar el journey.

## 3. Principios de Integración (Hoja de ruta 1B.3)
1. **Resolver autoridad Request → Proposal → Project**: Prioridad absoluta.
2. **Centralizar estados**: Migrar mappings divergentes a una capa de dominio única.
3. **Migración progresiva**: No reescribir la aplicación; extraer servicios, tipos y ViewModels de forma incremental.
4. **Integridad**: Mantener la seguridad RLS sin duplicar reglas en el frontend.

## 4. Estado final del diseño (1B2.8)
Se confirma que el modelo de diseño es sólido. La arquitectura propuesta (capa de dominio centralizada + servicios atómicos + ViewModels específicos para UI) es viable y necesaria.

1B2.8 — Revisión global del modelo
Ya hice el cruce completo de 1B2.1 → 1B2.7, la documentación que está en main, el código actual y el estado real de Supabase. No modifiqué código, documentos ni datos.
Y encontré algo importante: el modelo conceptual está bien encaminado, pero hay cuatro decisiones que debemos respetar obligatoriamente cuando entremos en 1B.3. No hace falta inventar 1B2.9 ni abrir otra rama.
Veredicto general
El modelo está suficientemente definido para pasar a 1B.3, pero 1B.3 debe comenzar resolviendo primero estas cuatro incompatibilidades.
1. Contradicción crítica: Propuesta aceptada vs RPC de Supabase
Este es el hallazgo más importante.
La especificación 1B2.5 define:
proposal pending
      ↓
accepted
      ↓
project
      ↓
projects.proposal_id = proposal.id
Pero Supabase actualmente tiene un trigger:
project_requests.status
      ↓
accepted
      ↓
sync_projects_from_accepted_request()
      ↓
CREATE projects
      ↓
proposal_id = NULL
      ↓
DELETE project_request
La función realmente hace eso: cuando project_requests.status pasa a accepted, crea el proyecto con proposal_id = NULL y elimina la solicitud. 
Esto contradice directamente 1B2.5.3–1B2.5.5.
Por tanto, antes de implementar aceptación de Propuestas, debemos decidir una única autoridad para ese flujo.
Decisión requerida en 1B.3
La autoridad debe ser:
acceptProposal()
      ↓
proposal
      ↓
project
      ↓
proposal_id
y la automatización antigua que convierte:
project_requests.accepted → project
no puede competir con eso.
Este es un bloqueo real de implementación.
2. Contradicción: Admin colapsa estados que son distintos
En admin.service.ts existe este mapping:
pending    → pendiente
evaluating → en_revision
accepted   → aprobada
rejected   → aprobada
canceled   → aprobada
Es decir:
rejected
canceled
terminan visualmente como:
aprobada
Eso contradice completamente la arquitectura que definimos en 1B2.5, donde:
pending
accepted
rejected
expired
son estados diferentes.
Por tanto, antes de implementar la capa compartida:
ese mapping debe desaparecer y sustituirse por el modelo común de dominio.

No debemos “parcharlo” en la UI.
3. Contradicción: progreso no tiene una sola fuente
Encontré tres conceptos diferentes de progreso:
Admin
Tiene valores manuales:
Análisis      25%
Producción    74%
Revisiones    82%
Completado   100%
y además mappings propios de estado.
Dashboard
project.service.ts calcula progreso desde los capítulos:
pendiente      0
cotizado      20
pagado        40
en_produccion 75
entregado    100
y, si no hay capítulos, vuelve a:
planning    25
production  60
review      85
completed  100
Supabase
Existe además:
production_stages
con:
progress_percentage
status
order_index
fechas
responsable
pero actualmente esa tabla tiene 0 filas.
Resultado
Hoy:
Admin progress
≠
Dashboard progress
≠
production_stages progress
Eso es exactamente lo que 1B2.7 estaba intentando eliminar.
Decisión
En 1B.3 debemos separar definitivamente:
ProjectStatus
de:
Progress
y no trasladar los porcentajes actuales de Admin como si fueran la verdad.
También es un prerrequisito real.
4. Contradicción: EditorialJourney aún no tiene todas sus fuentes conectadas
1B2.7 define correctamente que las seis fases deben derivarse de:
project_requests
evaluations
proposals
projects
reviews
y que deriveEditorialJourney() debe ser la única función que haga esa traducción. 
Pero el project.service.ts actual para Dashboard consulta principalmente:
projects
manuscripts
chapters
deliverables
y calcula el estado/progreso desde esos datos. 
No está construyendo todavía el contexto completo:
request
+
evaluation
+
proposal
+
project
+
reviews
Por tanto:
la arquitectura de las seis fases está diseñada, pero todavía no está soportada por el loader real.

No es un fallo del diseño. Es una tarea de implementación de 1B.3.
5. Lo que sí está coherente
Aquí la revisión global sale bastante bien.
Notificaciones
Tiene una estructura sana y compartida:
notification.service
        ↓
Dashboard + Admin

Feedback
reviews → deliverables → projects es una cadena coherente.
Timeline
Está correctamente definido como historial, no como fuente del estado.
Internal Notes
Está correctamente aislado:
Admin only
y Supabase mantiene RLS Admin-only.
Proposals
El modelo está bien diseñado; el problema es el flujo de activación existente, no la tabla.
Comunicación
Está correctamente separada de:

Timeline;
Notifications;

Internal Notes.
Eso coincide con la arquitectura documental. 
6. Supabase: otro hallazgo que debemos registrar
Supabase tiene funciones SECURITY DEFINER expuestas a anon/authenticated, y los advisors siguen señalándolas.
Entre ellas:
sync_project_request_from_manuscript()
sync_projects_from_accepted_request()
delete_manuscript_when_request_gone()
y funciones de limpieza relacionadas.
Los advisors las consideran un riesgo de seguridad porque están ejecutables mediante RPC público. 
Esto no bloquea 1B.3 por sí mismo, porque no vamos a reescribir Supabase ahora, pero sí debe quedar como riesgo explícito de implementación y no debemos añadir nuevas funciones privilegiadas sin una razón clara.
