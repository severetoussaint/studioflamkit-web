## — Auditoría real de Arquitectura cruzada Dashboard/Admin
Ya quedó auditado el estado actual de **`main`** y el proyecto Supabase **`studioflamkit`**. No modifiqué código, documentos ni datos.

El roadmap actual confirma que **1B2.7 = Arquitectura cruzada Dashboard/Admin** y que 1B2.1–1B2.6 ya están cerradas, mientras 1B2.7 sigue pendiente. 

---

# 1. Qué estamos auditando
La pregunta de esta fase es:

> **¿Dashboard y Admin están operando sobre el mismo modelo de negocio, con las mismas fuentes de verdad, o cada lado tiene su propia interpretación del sistema?**
La respuesta corta es:

> **Comparten Supabase, pero todavía no comparten una arquitectura de dominio única.**
Hay bastante reutilización de datos, pero también bastante lógica duplicada y varios caminos distintos para modificar el mismo concepto.

---

# 2. La arquitectura actual, simplificada
Hoy tenemos esto:

```
                    SUPABASE
                        │
        ┌───────────────┴────────────────┐
        │                                │
        ▼                                ▼
   DASHBOARD                         ADMIN
        │                                │
 project.service                 admin.service
 manuscript.service              admin.service.patch
 notification.service            lógica en admin/page.tsx
        │                                │
        └───────────────┬────────────────┘
                        ▼
                    mismas tablas
```
La base de datos es compartida.

Pero la **interpretación del negocio** no lo es completamente.

---

# 3. Dashboard del autor
El Dashboard oficial ya quedó consolidado en:

```
src/app/dashboard/page.tsx
```
y su arquitectura se apoya principalmente en servicios como:

- `project.service.ts`
- `manuscript.service.ts`
- `notification.service.ts`
El `project.service.ts` obtiene el proyecto del autor a partir de sus manuscritos y luego trae capítulos y entregables relacionados. 

Esto significa que Dashboard tiene una lógica propia de:

```
auth
 ↓
author
 ↓
manuscripts
 ↓
projects
 ↓
chapters
 ↓
deliverables
```

---

# 4. Admin
Admin utiliza:

```
src/services/admin.service.ts
src/services/admin.service.patch.ts
src/app/admin/page.tsx
```
y carga por separado:

```
project_requests
+
projects
```
En la propia página hay estados y lógica para:

- solicitudes;
- proyectos;
- selección de autor;
- selección de obra;
- capítulos;
- entregables;
- feedback;
- cambios de estado.
Esto crea el primer gran punto de duplicación:

> **Dashboard y Admin reconstruyen el contexto de una obra desde caminos diferentes.**

---

# 5. Duplicación nº 1 — estado del proyecto
Admin tiene su propio mapping:

```
planning  → analisis
production → produccion
review → revisiones
completed → completado
archived → completado
```
y también calcula progreso:

```
analisis     → 25%
produccion   → 74%
revisiones   → 82%
completado   → 100%
```
Eso está en `admin.service.ts`. 

Dashboard, por otro lado, tiene su propia arquitectura de recorrido editorial y ya se han hecho cambios para sincronizar su hero/journey con el estado editorial. 

### Problema
Tenemos:

```
ADMIN
  status mapping
  progress mapping

DASHBOARD
  editorial journey mapping
```
Dos interpretaciones del mismo estado.

Aunque ambas terminen mostrando algo parecido, **no existe una única capa de dominio que defina esas fases**.

---

# 6. Duplicación nº 2 — proyecto seleccionado
Admin tiene:

```
selectedAuthor
selectedProjectId
currentAuthor
currentAuthorProjects
activeProject
```
y además mantiene selects y pills para cambiar de obra dentro del mismo Admin. 

Dashboard ahora tiene su propio contexto de obra seleccionada y su propio flujo de múltiples manuscritos/obras, apoyado por los componentes extraídos en 1A.

La consecuencia:

> Ambos lados tienen el concepto de “obra activa”, pero no existe un único modelo compartido de `SelectedProjectContext`.
Eso no es necesariamente malo hoy, pero **sí es una duplicación arquitectónica que 1B2.7 debe ordenar**.

---

# 7. Duplicación nº 3 — carga de datos
Admin:

```
loadAllData()
 ├── listQuotationRequests()
 └── listAdminProjects()
```
Dashboard:

```
getAuthorRequestState()
getAuthorProjectData()
```
Es decir:

### Admin
pregunta:

> “¿Qué solicitudes y proyectos hay para administrar?”

### Dashboard
pregunta:

> “¿Qué estado y proyecto tiene este autor?”
Ambas respuestas terminan llegando a las mismas entidades principales.

Eso significa que tenemos distintas lecturas para el mismo dominio:

```
author
request
project
manuscript
```

---

# 8. Duplicación nº 4 — solicitudes
Admin convierte estados de base a:

```
pending
→ pendiente

evaluating
→ en_revision

accepted
→ aprobada

rejected
→ aprobada
canceled
→ aprobada
```
Este mapping es particularmente peligroso:

```
rejected → aprobada
canceled → aprobada
```
Eso significa que la UI de Admin **colapsa estados distintos de Supabase en el mismo estado visual**. 

Dashboard tiene su propia lógica de request state en `manuscript.service.ts`.

### Conclusión
No existe una única semántica transversal para `project_requests.status`.

Esto debe corregirse conceptualmente antes de implementación, no arreglarse con otra condición en una pantalla.

---

# 9. Duplicación nº 5 — cotización vs propuesta
Esto quedó clarísimo en 1B2.5.

Admin actualmente calcula cotización desde `word_count` y usa `project_requests`.

La función de actualización de solicitudes sigue trabajando directamente con:

```
project_requests.status
```
y el conversor actual hace:

```
createAdminProject(...)
↓
updateQuotationRequestStatus(..., aprobada)
```
Es decir:

```
cotización
→ proyecto
```
sin pasar realmente por:

```
proposal
```
Esto es exactamente la clase de arquitectura cruzada que 1B2.7 debe eliminar.

---

# 10. Problema nº 6 — Proyectos sin propuesta
En Supabase actualmente:

```
projects = 1
proposals = 0
project_requests = 0
```
y el proyecto real tiene:

```
proposal_id = null
status = production
```
Esto demuestra que la arquitectura actual permite:

```
Admin → proyecto
```
sin:

```
proposal → accepted → project
```
El modelo de base de datos está preparado para una relación más completa, pero la aplicación todavía tiene un camino alternativo.

---

# 11. Problema nº 7 — `production_stages`
Supabase tiene una tabla:

```
production_stages
```
con:

- `project_id`;
- `name`;
- `order_index`;
- `progress_percentage`;
- `status`;
- `start_date`;
- `end_date`;
- `assigned_to`;
- `notes`.
Pero actualmente:

```
production_stages = 0 filas
```
Mientras Admin calcula progreso desde `projects.status` y Dashboard tiene su propia representación editorial.

Eso crea una posible tercera fuente de verdad para progreso operativo:

```
projects.status
production_stages
editorialJourney
```

### Esta es una de las decisiones arquitectónicas más importantes de 1B2.7.

---

# 12. Problema nº 8 — Feedback
El modelo de feedback es:

```
projects
  ↓
deliverables
  ↓
reviews
```
Admin ya tiene una experiencia de comentario/feedback directamente sobre entregables. 

Dashboard todavía no tiene una experiencia equivalente completamente integrada.

Esto genera:

```
ADMIN
feedback = operativo

DASHBOARD
feedback = parcialmente representado / pendiente de integración
```
La especificación 1B2.3 ya resolvió conceptualmente esto, pero **la arquitectura cruzada todavía tiene que establecer que ambos consumen el mismo modelo**, no dos versiones visuales independientes. 

---

# 13. Problema nº 9 — Activity / Timeline
Supabase tiene:

```
timeline
```
relacionada con:

```
projects
```
pero:

```
timeline = 0 filas
```
Mientras Dashboard ya tiene concepto de editorial journey y Admin tiene actualizaciones de proyecto.

Por tanto actualmente:

```
Dashboard → muestra progreso/historial derivado
Admin → modifica estado
Supabase → timeline existe pero no es la fuente efectiva del historial
```
La arquitectura cruzada necesita cerrar el puente:

```
acción real
→ dominio
→ timeline
→ Dashboard/Admin
```
no:

```
Dashboard calcula historial
Admin calcula historial
```

---

# 14. Problema nº 10 — Notificaciones
Aquí tenemos una arquitectura mucho más sana.

Existe un servicio dedicado:

```
notification.service.ts
```
y la `Navbar` utiliza la misma infraestructura para mostrar la campana tanto en Dashboard como Admin. La auditoría de Comunicación ya documentó esa infraestructura como funcional. 

Esto nos da un patrón bueno:

```
shared service
      ↓
Admin
      +
Dashboard
```

### Esta es una arquitectura que debemos copiar para las demás capacidades.

---

# 15. Problema nº 11 — Comunicación
La auditoría ya confirmó que actualmente no existe:

```
messages
conversations
```
y que soporte, reviews, timeline, notifications, proposals e internal notes cubren responsabilidades diferentes. 

Así que Dashboard y Admin **no pueden todavía compartir un módulo real de mensajería**, porque todavía no existe la infraestructura.

La arquitectura de 1B2.2 ya lo dejó conceptualmente definido; 1B2.7 solo tendrá que garantizar que ambos lados consuman la misma capa cuando se implemente.

---

# 16. Problema nº 12 — Internal Notes
Aquí la separación es correcta:

```
Admin → internal_notes
Dashboard → nunca
```
y RLS lo confirma.

No necesitamos compartir esa capacidad entre ambos.

Esto es un buen ejemplo de:

> **arquitectura compartida no significa que todo aparezca en ambas interfaces.**

---

# 17. Problema nº 13 — Seguridad
Todas las tablas principales de dominio están con RLS habilitado:

- authors;
- manuscripts;
- project_requests;
- evaluations;
- proposals;
- projects;
- production_stages;
- deliverables;
- reviews;
- files;
- notifications;
- timeline;
- internal_notes;
- chapters.
Supabase confirma RLS habilitado en todas ellas.

Eso está bien.

### Pero hay una alerta independiente
Los advisors de Supabase detectan varias funciones `SECURITY DEFINER` expuestas a `anon` y `authenticated`, entre ellas:

- `sync_project_request_from_manuscript()`
- `sync_projects_from_accepted_request()`
- funciones de limpieza relacionadas.
Esto no significa que 1B2.7 deba modificar esas funciones ahora, pero **sí demuestra que existen caminos de negocio en la base que pueden operar fuera de las rutas explícitas de Dashboard/Admin**.

Ese es un riesgo arquitectónico real y deberá quedar registrado antes de implementar la integración cruzada.

# 19. El hallazgo principal
No tenemos un problema de:

> **“Admin y Dashboard usan tablas diferentes.”**
Tenemos uno más sutil:

> **Admin y Dashboard usan las mismas tablas, pero algunas reglas de dominio están duplicadas en ambos lados.**
Ese es exactamente el problema que 1B2.7 debe solucionar antes de 1B.3.

---

# 20. Qué debería ser compartido

### Compartir dominio

```
Project
ProjectStatus
ProjectPhase
RequestStatus
ProposalStatus
ReviewStatus
TimelineEvent
Notification
```

### Compartir servicios
Conceptualmente:

```
project.service
proposal.service
review.service
timeline.service
notification.service
communication.service
```
Pero Admin puede tener servicios de administración encima:

```
admin.service
```
que orquesten esos servicios, no que reinventen su lógica.

# 21. Qué NO debe compartirse
Admin-only:

```
internal_notes
evaluation details
admin controls
```
Autor-only:

```
proposal acceptance
own files
own messages
```
Shared backend:

```
project
proposal
review
timeline
notification
```

  ├── request state

Supabase

  ├── production_stages

  ├── timeline

Eso es demasiada duplicación para la misma experiencia.

# 24. Riesgos antes de 1B.3

### Alto
**Estado/fase del proyecto.**

Tenemos `projects.status`, mappings en Admin, journey en Dashboard y `production_stages`.

### Alto
**Ruta solicitud → propuesta → proyecto.**

Actualmente Admin puede saltar `proposals`.

### Alto
**Sincronización automática en Supabase.**

Existen funciones de sincronización que pueden crear/mover datos independientemente de la UI.

### Medio
**Feedback.**

Modelo común sí; presentación todavía asimétrica.

### Medio
**Timeline.**

Modelo común sí; alimentación real todavía no.

### Bajo
**Notifications.**

Es la pieza más compartida y mejor estructurada actualmente.

---

# 25. Veredicto 1B2.7.1
La arquitectura cruzada actual es:

> **misma base de datos, diferentes interpretaciones de negocio.**
Eso significa que **1B2.7 es absolutamente necesaria** antes de 1B.3.

Pero la buena noticia es que ya tenemos una base muy clara.

La solución no requiere rehacer Admin ni Dashboard.

Necesitamos definir una **capa de dominio compartida** que ambos consuman:

```
                 DOMAIN
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
  Dashboard      Admin       Supabase
```
Y las interfaces pueden seguir siendo diferentes.

### Lo que debe resolverse en 1B2.7.2
Ahora toca diseñar exactamente:

**qué servicios son compartidos, qué mappings dejan de vivir en `admin.service`, qué estado queda centralizado, qué datos debe consumir Dashboard, qué operaciones Admin puede orquestar, y qué funciones de Supabase no deben competir con la lógica de frontend.**

No tocaré código todavía. Ese será el **1B2.7.2 — Diseño funcional de la arquitectura cruzada**.
