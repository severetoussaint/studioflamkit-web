# Reglas de comportamiento de Arquitectura cruzada — 1B2.7.4

Este documento establece las reglas de negocio para asegurar la coherencia entre el Dashboard (Autor) y el panel de Admin, garantizando una única fuente de verdad y evitando la divergencia de estados.

## 1. Principio de Autoridad única
Cada concepto de negocio tiene una autoridad única (fuente de verdad):
- `project_requests` -> Solicitud
- `evaluations` -> Evaluación
- `proposals` -> Propuesta
- `projects` -> Proyecto
- `reviews` -> Feedback
- `timeline` -> Actividad
- `internal_notes` -> Notas internas

**Regla**: Dashboard y Admin consumen estas fuentes directamente a través de servicios de dominio. Ninguno está autorizado a reinterpretar o persistir estados propios.

## 2. Separación de Roles
- **Dashboard**: Consumidor de la experiencia del autor. Visualiza, acepta/rechaza propuestas, responde feedback, consulta hitos.
- **Admin**: Gestor de operaciones. Crea propuestas, evalúa, gestiona notas internas, modifica estados.
- **Independencia visual**: Ambos entornos pueden tener interfaces asimétricas mientras mantengan la integridad del modelo de negocio compartido.

## 3. Lógica de Dominio Centralizada
- **EditorialJourney**: La "Ruta editorial" (seis fases) es una proyección calculada a partir de los estados reales (`projects.status`, `reviews`, etc.) mediante la función `deriveEditorialJourney`. No se almacena como estado independiente.
- **Servicios**: La lógica reside en servicios de dominio (`proposal.service`, `review.service`, etc.). `admin.service` orquesta estas acciones, pero no duplica su lógica.

## 4. Integración y Sincronización
- **Atomicidad**: Las operaciones complejas (ej: Aceptación de propuesta + Activación de proyecto) deben ser atómicas y consistentes.
- **Idempotencia**: Las acciones de negocio (especialmente las que modifican estados) deben estar protegidas contra retries accidentales.
- **Deduplicación**: Se utiliza lógica de negocio explícita (ej: verificar estados previos) para evitar duplicidades.

## 5. Seguridad y RLS
- **Fuente de verdad de seguridad**: RLS en Supabase. La UI no es una barrera de seguridad; la lógica de backend valida siempre el acceso y la propiedad del proyecto.
- **Autorización de acciones**: Una acción permitida en el dominio (ej: `acceptProposal`) debe ser validada en backend sin confiar en el estado del cliente (Dashboard/Admin).

## 6. Comunicación y Eventos
- **Timeline**: Historial de acontecimientos confirmados (no ruido técnico).
- **Notificaciones**: Canal independiente de avisos.
- **Mensajes**: El canal para la discusión (sin contaminar los objetos de negocio con comentarios libres).

---

### Decisión final de 1B2.7.4
Se establece la regla de oro: **Una entidad, una fuente de verdad, una autoridad de dominio y múltiples experiencias de UI**. 

Se prohíbe explícitamente:
- Reinterpretar estados de negocio en la UI.
- Generar fuentes de verdad paralelas.
- Permitir que notificaciones o eventos de Timeline actúen como triggers de estados maestros.
- Dependencia bidireccional entre interfaces (Dashboard no controla Admin y viceversa).

*La arquitectura está lista. El siguiente y último paso es **1B2.7.5 — Especificación de implementación**, para detallar el plan de refactorización y consolidación.*


Vamos con 1B2.7.4 — Reglas de comportamiento de la arquitectura cruzada Dashboard/Admin.
Aquí cerramos las reglas que impedirán que la arquitectura nueva vuelva a caer en dos fuentes de verdad.
1. Regla de autoridad
Cada concepto tiene una sola autoridad de negocio.
Solicitud       → project_requests
Evaluación      → evaluations
Propuesta       → proposals
Proyecto        → projects
Producción      → production_stages
Feedback        → reviews
Actividad       → timeline
Notificación    → notifications
Comunicación    → conversations/messages
Nota interna    → internal_notes
Dashboard y Admin nunca crean una fuente alternativa para ninguno de ellos.
2. Dashboard es consumidor
Dashboard puede:
leer;
mostrar;
ejecutar acciones explícitamente permitidas al autor.
No puede reinterpretar ni guardar una versión propia del estado.
Ejemplo:
projects.status = production
Dashboard no guarda:
localStatus = "produccion"
como fuente persistente.
3. Admin es operador
Admin puede ejecutar operaciones administrativas autorizadas:
crear propuesta
cambiar proyecto
crear feedback
crear nota interna
subir entregable
Pero tampoco mantiene una copia paralela de esos estados.
4. Mismo dominio, distintos permisos
Ejemplo:
proposal
   ↓
Admin: crear/editar
Autor: aceptar/rechazar
Los dos usan proposalService.
Lo que cambia es la autorización.
No creamos:
adminProposalService
authorProposalService
para la misma operación de negocio.
5. La UI nunca decide permisos
Esto:
if (role === 'admin') {
   mostrar botón
}
sirve para UX.
Pero no es seguridad.
La operación real debe llegar a Supabase y pasar RLS/autorización.
6. Una escritura, una autoridad
Para cualquier acción importante:
UI
 ↓
servicio de dominio
 ↓
persistencia
No:
UI
 ↓
UPDATE tabla
 ↓
otro servicio
 ↓
RPC
 ↓
trigger
haciendo el mismo cambio otra vez.
7. Evitar efectos secundarios duplicados
Cuando una acción produce varias consecuencias:
Aceptar propuesta
    ├── proposal accepted
    ├── project activated
    ├── timeline event
    └── notification
la operación debe tener un solo orquestador.
No:
Dashboard crea notification
Admin crea timeline
Supabase RPC crea project
cada uno por su cuenta.
8. Operaciones transaccionales
Cuando varias escrituras son inseparables para mantener la consistencia, deben tratarse como una operación transaccional.
Ejemplo:
Aceptar propuesta
    ↓
accepted
    +
project.proposal_id
No puede quedar una parte confirmada y la otra perdida sin que exista una estrategia explícita de recuperación.
9. Regla de conflicto
Si Dashboard tiene datos antiguos:
Dashboard cargó:
production
y Admin acaba de cambiar:
→ review
la nueva operación y la siguiente lectura deben prevalecer.
El estado persistido gana frente al estado local.
10. Refresh
Después de una escritura importante:
write
 ↓
response real
 ↓
refresh/revalidate
No se debe depender solamente de:
setLocalState()
para fingir que la base cambió.
11. Optimistic UI
Puede utilizarse solamente para interacciones de bajo riesgo.
No para:
aceptar propuestas;
crear proyectos;
cambiar estados importantes;
eliminar datos;
decisiones editoriales.
En esos casos:
primero confirmación real, después UI definitiva.

12. EditorialJourney
Las seis fases son una representación derivada.
Nunca se guardan como estado independiente.
solicitud
evaluación
propuesta
proyecto
reviews
    ↓
EditorialJourney
Así no puede ocurrir:
projects.status = production
editorial_phase = proposal
por una desincronización manual.
13. Estado actual vs historial
Separación obligatoria:
Entidad de negocio
= estado actual

Timeline
= historial
Nunca reconstruir el estado actual leyendo el último evento de Timeline.
14. Timeline no es fuente de verdad
Aunque una entrada diga:
“Proyecto pasó a Producción”

la fuente actual sigue siendo:
projects.status
Timeline solo conserva el hecho histórico.
15. Notificaciones no son fuente de verdad
Una notificación:
“Tu propuesta fue aceptada”

no significa que la UI pueda asumir aceptación solamente porque recibió esa notificación.
Debe leer:
proposals.status
La notificación es un canal de aviso.
16. Communication no controla dominio comercial
Un mensaje no cambia automáticamente:
precio;
servicios;
revisiones;
deadline;
propuesta;
proyecto.
Una conversación puede desencadenar una acción explícita, pero no modificar datos de negocio por sí misma.
17. Internal Notes
Nunca producen automáticamente:
Timeline público;
Notifications al autor;
Messages;
cambios de estado.
Son completamente privadas.
18. Feedback
Una review puede cambiar su propio estado:
open → resolved
pero no debe modificar projects.status arbitrariamente solo porque fue resuelta.
Si existe una regla futura que conecte ambas cosas, se implementará en el servicio de dominio correspondiente.
19. Propuestas
Una propuesta aceptada puede activar un proyecto.
Pero el proyecto no debe aparecer como activo antes de que la operación de aceptación se confirme.
La secuencia conceptual es:
pending
 ↓
accepted
 ↓
project
20. Requests y Proposals
Una solicitud y una propuesta no son sinónimos.
Puede existir:
request
 ├── proposal A → rejected
 └── proposal B → pending
La solicitud conserva su contexto.
La propuesta conserva su historial comercial.
21. Supabase RPC vs servicios
Las funciones RPC existentes que realizan sincronizaciones deben clasificarse antes de usarlas como parte de nuevas operaciones.
Si una función ya es la autoridad transaccional de una operación:
el servicio la llama.

Si el servicio ya hace esa operación:
no duplicamos el mismo trabajo con otra RPC.

Si una función resulta ser legacy o duplicada:
se documenta y se deja fuera del nuevo flujo hasta que una fase de limpieza la retire.

22. Triggers
No usar triggers simplemente porque “pueden automatizarlo”.
Un trigger solo se justifica cuando:
la regla debe cumplirse independientemente del cliente;
debe ocurrir siempre en la base;
y no existe riesgo de duplicar la misma lógica.
Esto es especialmente importante para Timeline y sincronizaciones.
23. RLS
RLS permanece como última autoridad de acceso.
La arquitectura de servicios no sustituye:
USING
WITH CHECK
y cualquier nuevo UPDATE debe respetar también la necesidad de una política de lectura correspondiente.
24. Admin-only
Estas capacidades quedan fuera del Dashboard:
Internal Notes
Evaluation details internos
Controles administrativos
No debemos forzar “simetría” entre interfaces.
25. Autor-only
Estas acciones corresponden al autor:
Aceptar propuesta
Rechazar propuesta
Leer sus notificaciones
Interactuar con sus mensajes
Consultar feedback permitido
Admin no necesita una segunda versión de esas mismas reglas; usa el mismo dominio con permisos administrativos distintos.
26. Selección de proyecto
La selección de proyecto es estado de interfaz.
No se debe utilizar como fuente de autorización.
Ejemplo:
selectedProjectId
no significa que el usuario tenga derecho a acceder a ese proyecto.
La consulta real y RLS deben verificarlo.
27. Cambiar de proyecto
Cuando cambia:
Project A → Project B
todas las capacidades contextuales deben cambiar juntas:
capítulos;
entregables;
feedback;
timeline;
propuestas;
notas internas si es Admin.
No puede quedar un panel mostrando datos de A mientras el encabezado dice B.
28. Carga parcial
Si una pieza falla:
Timeline error
Dashboard no debe ocultar silenciosamente el error ni inventar un timeline.
La interfaz debe mostrar el fallo solo en ese módulo y mantener disponible lo demás.
Esto es especialmente importante al crecer el workspace.
29. Errores de dominio
El servicio debe diferenciar:
not found
unauthorized
invalid transition
expired
conflict
database error
para que Dashboard y Admin puedan reaccionar correctamente.
No debemos presentar todos como:
“Ocurrió un error.”

30. Reintentos
Los reintentos automáticos solo se permiten para errores realmente transitorios.
No repetir operaciones de negocio no idempotentes sin protección.
Especialmente:
aceptar propuesta;
crear proyecto;
crear propuesta;
eliminar proyecto.
31. Compatibilidad progresiva
Durante 1B.3:
código actual
   ↓
extraer dominio
   ↓
migrar consumidor
   ↓
verificar
   ↓
eliminar duplicado
Nunca romper Dashboard y Admin simultáneamente para luego “arreglarlo”.
32. Regla de reutilización
Antes de crear:
nuevo service
nuevo hook
nuevo component
comprobar:
¿ya existe una pieza que tenga exactamente esa responsabilidad?

Pero no reutilizar una pieza por nombre si internamente hace otra cosa.
33. Regla para componentes
Compartir:
datos;
dominio;
comportamiento común.
No necesariamente:
layout;
densidad;
navegación;
copy;
jerarquía visual.
Así Admin y Dashboard pueden seguir teniendo diseños distintos.
Matriz de autoridad final
Concepto	Fuente de verdad	Dashboard	Admin
Solicitud	project_requests	leer	leer/modificar
Evaluación	evaluations	solo salida permitida	leer/modificar
Propuesta	proposals	leer/decidir	crear/modificar
Proyecto	projects	leer	modificar
Producción	production_stages	leer lo necesario	operar
Feedback	reviews	leer/interactuar	crear/gestionar
Actividad	timeline	leer	leer/registrar vía dominio
Notificaciones	notifications	leer	generar
Comunicación	messages/conversations	usar	usar
Notas internas	internal_notes	nunca	usar


Decisión cerrada de 1B2.7.4
La regla principal queda:
Una entidad, una fuente de verdad, una autoridad de dominio y múltiples experiencias de UI según el usuario.

Y las dos interfaces quedan sincronizadas por el dominio y la persistencia, no mediante estados React compartidos ni mediante comunicación directa entre Dashboard y Admin.
Esto cierra la parte de comportamiento de 1B2.7.
El siguiente y último paso de esta rama es 1B2.7.5 — Especificación de implementación, donde voy a convertir todo esto en un plan técnico concreto de migración: qué archivos se tocan, qué servicios se extraen, qué tipos se crean, qué duplicados se eliminan y en qué orden debe hacerse sin romper el Dashboard actual.
