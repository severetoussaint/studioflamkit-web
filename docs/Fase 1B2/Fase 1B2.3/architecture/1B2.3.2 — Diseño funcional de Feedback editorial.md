# Diseño funcional de Feedback editorial — 1B2.3.2

Esta subfase no busca inventar un sistema paralelo, sino convertir la lógica existente en `reviews` en una experiencia editorial coherente tanto para Admin como para el Dashboard del Autor.

## 1. Objetivo
El feedback editorial debe responder: **¿Qué se revisó? → ¿Qué observación existe? → ¿Quién debe actuar? → ¿Qué estado tiene? → ¿Qué pasó después?**

## 2. Separación de conceptos
- **Review / Feedback**: Observación editorial sobre una entrega.
- **Mensaje**: Conversación libre (motor de comunicación 1B2.2).
- **Notificación**: Aviso del sistema.
- **Timeline**: Historial de acontecimientos.
- **Internal note**: Información privada del Admin.

## 3. Dashboard del autor
Cada proyecto tendrá su propia sección dedicada:
```
Mi obra
├── Ruta editorial
├── Biblioteca
├── Feedback editorial
└── Mensajes
```
El "Feedback editorial" mostrará tarjetas con la entrega, descripción, estado (ej: Pendiente) y fecha.

## 4. Ciclo de vida y roles
- **Estados**: `Pendiente` → `En revisión` → `Resuelto`.
- **Admin**: Puede crear, modificar, responder y marcar como resuelto.
- **Autor**: Puede leer y responder, pero no cambiar el estado a "Resuelto" sin una acción editorial previa.

## 5. Contexto y Relaciones
El feedback debe mantener la relación con el `Proyecto` y, donde sea posible, con el `Deliverable` (entregable) asociado. Esto asegura que la observación editorial no pierda su referencia original.

## 6. Vista del detalle
Interfaz dedicada para visualizar la observación y el hilo de respuesta. El objetivo es que, posteriormente, el usuario pueda saltar desde esta vista a una conversación (vía el motor de mensajes 1B2.2) si necesita discutir la observación.

## 7. Experiencia Admin
Interfaz operativa que permita filtrar (Todos, Pendientes, En revisión, Resueltos) y realizar acciones masivas o individuales sobre la gestión del feedback. Se incluye un formulario de "Nuevo feedback" para crear observaciones vinculadas a obras y entregas específicas.

## 8. Tipos de feedback
Categorías simplificadas para filtrado inicial:
- Corrección editorial, Contenido, Formato, Audio, Archivo, Otro.

## 9. Integración con otros módulos
- **Ruta editorial**: Es el progreso del proyecto (distinto del feedback que es la observación puntual).
- **Mensajes**: El feedback es el objeto editorial; los mensajes son la conversación alrededor.
- **Notificaciones**: Avisos sobre creación/actualización de feedback.
- **Timeline**: Historial de estados del feedback (sin duplicar el contenido).

## 10. Primera versión (MVP)
Circuito completo:
1. Admin crea feedback.
2. Autor recibe notificación.
3. Autor ve y responde.
4. Admin actualiza estado tras respuesta.
5. Autor recibe notificación de actualización.

## 11. Lo que dejamos para después
No se incluye: revisiones automáticas por IA, métricas, SLA, anotaciones sobre PDF o comentarios por palabra.

### Resultado de 1B2.3.2
El Feedback editorial se formaliza como una sección propia en el Dashboard. No reemplaza a Ruta editorial, Mensajes o Notificaciones.

Seguimos con 1B2.3.2 — Diseño funcional de Feedback editorial.
Aquí no vamos a inventar un sistema paralelo: vamos a tomar lo que ya existe en reviews y convertirlo en una experiencia editorial coherente para Admin + Dashboard.
1. Objetivo
El feedback editorial debe responder claramente:
¿Qué se revisó? → ¿Qué observación existe? → ¿Quién debe actuar? → ¿Qué estado tiene? → ¿Qué pasó después?

Y debe estar relacionado con la obra/proyecto correspondiente.
2. Separación de conceptos
Queda así:
Review / Feedback
→ observación editorial sobre una entrega.
Mensaje
→ conversación libre entre autor y equipo.
Notificación
→ aviso de que algo ocurrió.
Timeline
→ historial de acontecimientos.
Internal note
→ información privada de Admin.
No convertiremos una review en un chat.
3. Dashboard del autor
Propongo que cada proyecto tenga una sección:
Mi obra
├── Ruta editorial
├── Biblioteca
├── Feedback editorial
└── Mensajes
Feedback editorial
Mostraría tarjetas de observaciones:
Feedback editorial

┌─────────────────────────────────┐
│ Capítulo 3                      │
│ Corrección editorial            │
│                                 │
│ "Revisar transición entre..."   │
│                                 │
│ Estado: Pendiente               │
│ Hace 2 horas                    │
│                                 │
│ [Ver feedback]                  │
└─────────────────────────────────┘
4. Estados
No usaría los seis estados de la Ruta editorial aquí.
Son conceptos distintos.
Para feedback necesitamos algo pequeño:
Pendiente
En revisión
Resuelto
Y posiblemente:
Cerrado
pero inicialmente Pendiente → En revisión → Resuelto es suficiente.
5. ¿Quién puede cambiar el estado?
La regla inicial:
Admin
Puede:
crear feedback;
modificarlo;
cambiar su estado;
responder;
marcarlo resuelto.
Autor
Puede:
leerlo;
responder;
indicar que realizó la corrección.
Pero no debería poder simplemente cambiar arbitrariamente:
Pendiente → Resuelto

sin que exista una acción editorial detrás.
6. Feedback dentro del proyecto
El feedback debe tener contexto.
Idealmente:
Feedback
   ↓
Proyecto
   ↓
Obra
Y cuando sea posible:
Feedback
   ↓
Deliverable
Esto es importante porque actualmente reviews ya está conectado con deliverables.
No queremos perder esa relación.
7. Vista del detalle
Al pulsar:
Ver feedback
abrimos:

                         [Responder]
Así podemos posteriormente enlazar:
Feedback ↔ conversación
sin convertir uno en el otro.

Formulario:

Esto es importante porque la auditoría detectó que muchas capacidades existen en backend pero no tienen una interfaz administrativa equivalente.
10. Tipos de feedback
No crearía veinte categorías.
Inicialmente:
Corrección editorial
Contenido
Formato
Audio
Archivo
Otro
Esto nos permite filtrar y mostrar contexto sin sobrediseñar.
11. Relación con la Ruta editorial
Aquí hay que ser muy cuidadosos.
La Ruta editorial:
Recibido → Análisis → Propuesta → Producción → Revisión → Completado

es el progreso del proyecto.
El feedback:
Pendiente → En revisión → Resuelto

es el estado de una observación concreta.
Son dos ejes diferentes.
Ejemplo:
Proyecto:
Producción

Feedback:
Pendiente
Eso es perfectamente válido.
12. Relación con mensajes
Si el autor necesita discutir una observación:
Feedback
   │
   └── [Hablar sobre esto]
              ↓
        conversación
Eso será especialmente útil después de implementar 1B2.2.
Así:
Feedback = objeto editorial.

Mensajes = conversación alrededor del objeto.

13. Relación con notificaciones
Cuando Admin crea feedback:
Feedback creado
      ↓
Notification
"Nuevo feedback editorial"
Cuando Admin cambia el estado:
Feedback actualizado
      ↓
Notification
"El feedback de Capítulo 3 fue actualizado"
Pero nuevamente:
la notificación no es el feedback.
14. Relación con Timeline
Podemos registrar eventos importantes:
Timeline
├── Feedback creado
├── Feedback actualizado
└── Feedback resuelto
Pero el detalle completo permanece en reviews.
Esto mantiene Timeline como historial, no como base de datos duplicada.
15. Diseño visual
Quiero que el feedback se sienta parte del Dashboard actual.
No una pantalla que parezca de otra aplicación.
Usaría:
mismas tarjetas;
mismos badges;
mismo sistema de colores;
iconos existentes;
mismo sidebar;
mismo responsive.
En Admin podemos aumentar la densidad de información.
16. Primera versión
La primera implementación funcional debería cubrir solamente:
ADMIN
Crear feedback
      ↓
Autor recibe notificación
      ↓
Autor ve feedback
      ↓
Autor responde
      ↓
Admin ve respuesta
      ↓
Admin actualiza estado
      ↓
Autor recibe actualización
Eso ya sería un sistema editorial útil.
17. Lo que dejamos para después
No implementaría todavía:
revisiones automáticas por IA;
asignación a múltiples editores;
prioridades complejas;
SLA;
estadísticas;
métricas de productividad;
versionado sofisticado;
anotaciones directamente sobre PDF;
comentarios por palabra/frase;
adjuntos específicos del feedback.
Primero hacemos que el circuito básico funcione de extremo a extremo.
Resultado de 1B2.3.2
La propuesta queda:
Feedback editorial será una sección propia dentro del contexto de cada proyecto/obra.
No reemplaza:
Ruta editorial;
Mensajes;
Notificaciones;
Timeline.
Y se convierte en el lugar donde vive la observación editorial estructurada.
