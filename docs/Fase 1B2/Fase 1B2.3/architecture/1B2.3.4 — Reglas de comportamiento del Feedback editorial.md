# Reglas de comportamiento del Feedback editorial — 1B2.3.4

Este documento define la lógica de negocio y comportamiento del Feedback editorial. El principio rector es mantener la separación entre la observación estructurada (`reviews`) y la comunicación/discusión (`mensajes`).

## 1. Creación de feedback
- **Acción**: Solo Admin puede crear un feedback tras identificar una observación sobre un entregable.
- **Regla**: No se crea automáticamente por cambios de fase en la Ruta editorial.

## 2. Gestión de Estados
- **`open` (Pendiente)**: Feedback que requiere atención.
- **`resolved` (Resuelto)**: Estado final tras una acción explícita de Admin.
- **`discarded` (Descartado)**: Observación que pierde vigencia. El historial se conserva (no se borra físicamente).

## 3. Interacción y Comunicación
- **Respuesta**: Cuando el autor responde a un feedback, se utiliza el motor de **Comunicación** (1B2.2), no se modifica el campo `comment` de la `review`.
- **Independencia**: Las respuestas no modifican el estado de la `review`. La resolución es una acción editorial explícita.

## 4. Notificaciones
- Se dispara una notificación al Autor cuando Admin crea un feedback o cambia su estado.
- La notificación apunta al contexto: `Proyecto` -> `Deliverable` -> `Feedback`.

## 5. Integración con otros módulos
- **Comunicación**: El feedback es el objeto editorial; los mensajes son el vehículo de discusión asociado.
- **Ruta editorial**: El progreso del proyecto es independiente del estado del feedback. Una obra puede estar en fase de "Producción" con feedback "Pendiente".
- **Timeline**: Registra eventos clave (`created`, `resolved`, `discarded`), pero la fuente de verdad es la tabla `reviews`.
- **Internal Notes**: Privadas para Admin, no mezcladas con el feedback visible para el autor.

## 6. Seguridad y Sincronización
- **RLS**: Barrera principal de acceso. Los autores solo acceden a sus proyectos.
- **Sincronización**: `reviews.status` es la fuente única de verdad. La UI no debe depender de estados locales independientes que puedan desincronizarse.

---

## Flujo Completo
1. **Admin**: Crea observación -> `reviews.insert` -> `Notification` -> **Autor**.
2. **Autor**: Lee -> Responde (vía **Comunicación**).
3. **Admin**: Evalúa respuesta -> Cambia `reviews.status` -> `Notification` -> **Autor**.

---

## Decisión cerrada
La lógica queda establecida: **`reviews` controla el estado editorial; `Comunicación` maneja la conversación; `Notificaciones` informa; `Timeline` registra; `Ruta editorial` controla el progreso del proyecto.** 

Esta separación evita los conflictos de ambigüedad funcional detectados en la auditoría.

1B2.3.4 — Reglas de comportamiento del Feedback editorial.
Aquí cerramos la lógica antes de pasar a la especificación de implementación.
1. Creación de feedback
Una review se crea cuando Admin identifica una observación concreta sobre un entregable.
Admin
  ↓
selecciona proyecto
  ↓
selecciona entregable
  ↓
escribe observación
  ↓
crea review
No se crea automáticamente porque cambie una fase de la Ruta editorial.
2. Estado inicial
Toda review nueva comienza:
open
En la UI lo podemos presentar como:
Pendiente

No necesitamos crear otro estado en Supabase solo para cambiar el texto visible.
3. open
Significa:
Existe una observación que todavía requiere atención.

Puede significar que:
el autor todavía no la ha visto;
el autor está trabajando en ella;
Admin está esperando una corrección.
No vamos a intentar representar todos esos matices dentro de reviews.status.
4. resolved
resolved significa:
El punto editorial ya no requiere trabajo.

La resolución debe ser una acción explícita.
No se marca automáticamente simplemente porque:
el autor abra el feedback;
responda;
suba un archivo;
cambie la fase del proyecto.
5. discarded
Significa:
La observación deja de ser aplicable.

Por ejemplo:
Admin pidió modificar una sección, pero posteriormente se decide eliminar esa sección completa.

No significa “borrado”.
La review permanece en el historial.
6. Autor responde
Aquí hacemos la separación fundamental:
Review
  │
  └── "Responder"
          ↓
     Comunicación
La respuesta no modifica reviews.comment.
Tampoco crearemos una columna author_response improvisada.
La respuesta será un mensaje asociado contextualmente al feedback cuando integremos Comunicación.
7. Admin responde
Mismo principio:
Review
  │
  └── "Responder"
          ↓
     Comunicación
No duplicamos el contenido en reviews.
8. Notificación
Cuando Admin crea una review:
review creada
    ↓
notification
    ↓
autor
Mensaje conceptual:
Nuevo feedback editorial

La notificación debe llevar al contexto correcto:
proyecto → entregable → feedback.

9. Actualización
Si Admin cambia:
open → resolved
o:
open → discarded
el autor puede recibir una notificación:
El feedback de [entrega] fue actualizado.

No generamos una conversación automáticamente.
10. ¿Cuándo aparece Comunicación?
Solo cuando alguien decide conversar.
Por ejemplo:
Feedback:
"Revisar transición del capítulo 3"

[Responder]
El usuario pulsa Responder.
Entonces:
conversation
   ├── project_id
   ├── contexto del feedback
   └── messages
Esto mantiene la diferencia entre:
feedback estructurado
y:
discusión sobre ese feedback.
11. Archivos
Subir un archivo nuevo no resuelve automáticamente una review.
Esto es importante.
Ejemplo:
Review:
"Corregir capítulo 3"

Autor sube:
capitulo-3-v2.docx
La review continúa open hasta que Admin determine que está resuelta.
Esto evita automatizaciones peligrosas.
12. Ruta editorial
Una review tampoco cambia automáticamente las seis fases:
Recibido
Análisis
Propuesta
Producción
Revisión
Completado
La review pertenece al eje editorial.
La ruta pertenece al progreso del proyecto.
Ejemplo perfectamente válido:
Proyecto: Producción
Review: Pendiente
o:
Proyecto: Revisión
Review: Resuelto
No hay contradicción.
13. Biblioteca
La biblioteca muestra archivos.
El feedback puede apuntar a un archivo mediante file_path, pero:
Biblioteca ≠ Feedback.

No vamos a duplicar archivos dentro de reviews.
14. Timeline
Eventos importantes pueden aparecer en Timeline:
Feedback creado
Feedback resuelto
Feedback descartado
Pero Timeline no será la fuente maestra.
La fuente será:
reviews
Timeline solamente representa el historial.
15. Notificaciones
La fuente maestra sigue siendo:
reviews
La notificación solo comunica el evento.
reviews
   ↓
notifications
Nunca:
notifications
   ↓
reviews
16. Internal Notes
Admin puede utilizar una nota interna para comentar algo que no debe ver el autor.
Eso permanece completamente separado:
Review
    ↓
visible al autor

Internal Note
    ↓
solo Admin
No debemos permitir que una nota interna aparezca accidentalmente como feedback.
17. Eliminación
No borramos reviews resueltas.
El historial editorial tiene valor.
Por tanto:
open
 ↓
resolved
no:
open
 ↓
DELETE
18. Regla de seguridad principal
El autor nunca debe poder modificar arbitrariamente el feedback de otro proyecto.
La autorización real viene de RLS.
La UI no será nuestra barrera de seguridad.
19. Regla de sincronización
No habrá dos fuentes de verdad.
Para cada review:
reviews.status
      ↓
estado visible del feedback
No:
reviews.status
       +
React state independiente
       +
timeline status
       +
notification status
La UI puede tener estado temporal para interacción, pero al recargar debe reconstruirse desde Supabase.
Flujo completo
ADMIN
  │
  │ crea observación
  ▼
REVIEWS
  │
  ├──────────────► NOTIFICATION ─────► AUTOR
  │
  ▼
DASHBOARD
  │
  │ autor abre feedback
  │
  ├── leer
  │
  └── responder
          │
          ▼
     COMUNICACIÓN
          │
          ▼
        ADMIN
          │
          │ evalúa corrección
          ▼
   reviews.status
          │
       ┌──┴──────┐
       ▼         ▼
   resolved   discarded
       │         │
       └────┬────┘
            ▼
       notification
Decisión cerrada
Para 1B2.3.4 queda establecido:
reviews controla el estado editorial. Comunicación controla la conversación. Notifications informa. Timeline registra. Internal Notes permanece privado. La Ruta editorial controla el progreso del proyecto.

Eso evita precisamente el problema que detectamos al principio: intentar hacer que una misma cosa controle cinco conceptos diferentes.
