# Modelo técnico de Feedback editorial — 1B2.3.3

Este documento define la arquitectura técnica para la gestión del feedback editorial, aprovechando las capacidades existentes en `reviews`.

## 1. Base técnica: `reviews`
Reutilizaremos la tabla `reviews` existente, ya que posee el esquema necesario para feedback estructurado:
- `deliverable_id`, `chapter_title`, `comment`, `file_path`, `status`, `created_at`.
- La asociación con la obra/proyecto ya está garantizada al colgar `deliverables` de `projects`.

## 2. Modelo de datos
`reviews` representa una **observación editorial estructurada** sobre un entregable.
- **Relación**: `Proyecto` -> `Deliverable` -> `Review`.
- **Estados**:
  - `open`: Feedback pendiente.
  - `resolved`: Punto resuelto.
  - `discarded`: Punto descartado.

## 3. Responsabilidades de `reviews`
### Reutilizamos:
- Observación editorial principal.
- Vínculo con el entregable (`deliverable_id`).
- Contexto de capítulo/archivo.
- Estado del feedback.
- RLS existente (autor lee sus proyectos, admin gestiona).

### Dejamos fuera:
- Conversación, mensajes encadenados.
- Notificaciones, timeline, soporte.
- Adjuntos del chat.
- Múltiples participantes.

## 4. Arquitectura de interacción (Admin - Dashboard)
- **Admin**: Crea, modifica, resuelve/descarta.
- **Dashboard**: Autor lee observaciones y estados. Si necesita discutir, se redirige al módulo de **Comunicación** (1B2.2).

## 5. Seguridad (RLS)
Se mantiene la política actual: el autor accede a `reviews` vinculadas a sus proyectos, mientras que Admin tiene acceso completo para gestión editorial.

## 6. Integración conceptual
```
Admin crea review (reviews.insert)
  ↓
RLS permite lectura al autor
  ↓
Dashboard muestra review
  ↓
Autor responde (usando motor de Comunicación 1B2.2)
  ↓
Admin resuelve/actualiza estado en review
```
*El feedback es el objeto editorial; los mensajes son el vehículo para discutirlo.*

## 7. Decisión técnica
**No se requiere ampliar `reviews` para esta etapa**. La tabla actual satisface el núcleo del feedback editorial estructurado. Cualquier necesidad futura de hilos de comentarios, respuestas internas o historial de intercambio se gestionará mediante el motor de **Comunicación**, manteniendo el Feedback como una pieza limpia y estructurada.
