# Especificación de implementación — 1B2.3.5

Este documento define el contrato técnico para la implementación del Feedback editorial, basado en la reutilización de la estructura existente.

## 1. Estrategia de persistencia
**No crearemos una tabla nueva**. Utilizaremos la tabla `reviews` existente, manteniendo la relación jerárquica: `projects` -> `deliverables` -> `reviews`.

## 2. Backend y Servicios
- **Entidad `reviews`**: Mantenemos los campos actuales (`id`, `deliverable_id`, `chapter_title`, `comment`, `file_path`, `status`, `created_at`). No añadiremos campos de mensajería (responsabilidad de 1B2.2).
- **Servicio**: Reutilizaremos `src/services/admin.service.ts` o crearemos `review.service.ts` si la lógica actual en `admin.service.patch.ts` es demasiado compleja o está acoplada. Operaciones: `getReviewsForDeliverable`, `createReview`, `updateReviewStatus`.

## 3. Experiencia de Usuario (UI)
- **Admin**: Nueva interfaz operativa para gestionar feedback, con filtrado por estado y formulario "Nuevo feedback".
- **Dashboard Autor**: Sección dedicada "Feedback editorial" dentro de cada proyecto.
- **Componentes**: `FeedbackCard`, `FeedbackStatusBadge`, `FeedbackDetail`. Compartidos entre Admin y Dashboard para coherencia, manteniendo diseños adaptados a la densidad de cada rol.

## 4. Estados y Sincronización
- **Mapeo visual**: `open` -> Pendiente, `resolved` -> Resuelto, `discarded` -> Descartado.
- **Fuente única de verdad**: El estado siempre se consulta desde Supabase; la UI no mantendrá estados independientes para evitar desincronizaciones.

## 5. Integración con otros módulos
- **Comunicación (1B2.2)**: El botón "Responder" en el feedback redirigirá al motor de Mensajes, manteniendo la separación entre el feedback (objeto) y el mensaje (conversación).
- **Notificaciones**: Se dispararán al crear/actualizar feedback, utilizando la infraestructura actual.
- **Timeline**: Registra eventos clave (`created`, `resolved`, `discarded`), sin ser la base de datos de consulta.
- **RLS**: Se mantiene el modelo actual: Autor accede a sus proyectos, Admin gestiona el total.

## 6. Pruebas Funcionales
- **Admin**: Creación, edición de estados y acceso restringido.
- **Autor**: Visualización, recepción de notificaciones y respuesta (integración con Comunicación).
- **Sincronización**: Verificación de actualización en tiempo real (vía refresco, no realtime forzado).
- **Seguridad**: Validación estricta de RLS por proyecto.

## 7. Orden de implementación
1. Auditoría y extracción de lógica de `reviews`.
2. Construcción de componentes (`FeedbackCard`, `FeedbackStatusBadge`, `FeedbackDetail`).
3. Integración en Admin.
4. Integración en Dashboard.
5. Integración de notificaciones.
6. Integración del flujo de respuesta con el motor de Comunicación.
7. Pruebas de seguridad y flujo de datos completo.

## 8. Lo que queda fuera (MVP)
No se implementará: chat nativo en reviews, comentarios anidados, adjuntos dentro de la review, IA, métricas avanzadas.
