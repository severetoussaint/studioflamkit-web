# Modelo técnico de Actividad / Timeline — 1B2.4.3

Este documento define la arquitectura técnica para la persistencia y gestión de la actividad del proyecto (`timeline`), estableciendo una clara separación entre fuentes maestras y la proyección histórica.

## 1. Estrategia de datos
- **Fuentes maestras**: Las tablas de negocio existentes (`projects`, `production_stages`, `reviews`, `proposals`, `conversations`) mantienen la integridad de los datos.
- **Proyección histórica (`timeline`)**: La tabla `timeline` funciona como un historial de hitos relevantes, no como un estado dinámico ni como base de datos duplicada.

## 2. Modelo técnico
Reutilizamos la estructura existente en Supabase:
- `id`: PK
- `project_id`: FK (Obligatorio, facilita RLS y agrupación)
- `event`: String (Clave estable, ej: `project_stage_changed`)
- `details`: String (Contexto legible breve)
- `created_at`: Timestamp

## 3. Comportamiento de escritura
- **Momento**: La escritura debe ocurrir atómicamente junto con la acción de negocio (dentro del mismo servicio/transacción).
- **Fuente**: El registro se concentra en los servicios de negocio (`project.service`, `review.service`, etc.), evitando el uso de triggers en base de datos para la lógica principal para mantener la trazabilidad y simplicidad.
- **Evitar duplicidad**: Se aplicarán reglas de deduplicación en la capa de servicio (evitando registros redundantes ante reintentos de red).

## 4. Gestión de eventos
- **Eventos estables**: `event` no será el texto mostrado en UI, sino una clave constante. La UI es responsable de traducir/formatear esta clave.
- **`details`**: Contexto descriptivo breve (evitar JSON complejos o duplicación masiva de datos).

## 5. RLS y Seguridad
- **Autor**: Acceso condicionado a `projects.author_id`.
- **Admin**: Acceso completo.
- No se requiere una nueva jerarquía de permisos.

## 6. Integración y flujo de datos
- **Integridad**: `timeline` nunca es la fuente de verdad para el estado de una entidad (ej: `projects.status` siempre prevalece sobre `timeline`).
- **Separación**: Las notificaciones (`notifications`) y el historial (`timeline`) tienen caminos independientes tras el evento de negocio.

## 7. Decisión técnica
**La tabla `timeline` reutiliza su esquema actual.** No se requieren cambios en Supabase ni nuevas tablas en esta etapa. El sistema se basa en la generación explícita de registros de actividad desde los servicios de negocio, asegurando que Timeline sea una proyección confiable del historial del proyecto.

### Estado final: 1B2.4.3 — Modelo técnico cerrado.
*El siguiente paso será **1B2.4.4 — Reglas de comportamiento**, para definir el catálogo exacto de eventos y sus disparadores.*


Vamos con 1B2.4.3 — Modelo técnico de Actividad / Timeline.
La regla base será: timeline es una proyección histórica; las tablas de negocio siguen siendo las fuentes maestras.
1. Fuente de verdad
Información	Fuente maestra	Timeline
Estado actual del proyecto	projects.status	registra el cambio
Etapas operativas	production_stages	registra hitos
Feedback	reviews	registra creación/resolución
Propuesta	proposals	registra eventos relevantes
Mensajes	conversations/messages	solo eventos importantes
Notificaciones	notifications	no alimentan Timeline


La tabla timeline ya existe y hoy tiene project_id, event, details, created_at; además tiene relación directa con projects. 
2. Modelo de timeline
Reutilizamos la estructura actual:
timeline
├── id
├── project_id
├── event
├── details
└── created_at
No añadimos todavía source_type, source_id ni una tabla de eventos genérica.
Quiero evitar ampliar el esquema hasta que demostremos que realmente lo necesitamos.
3. event
event será una clave estable, no el texto mostrado.
Ejemplos:
project_created
project_stage_changed
project_completed

chapter_created
chapter_delivered

deliverable_created
deliverable_approved

review_created
review_resolved
review_discarded

proposal_created
proposal_accepted
proposal_rejected
La UI traducirá esas claves:
project_stage_changed
→ "El proyecto pasó a Producción"
Así no dependemos de textos españoles almacenados en la base.
4. details
details será el contexto legible del evento.
Ejemplo:
"De Análisis a Producción"
o:
"Capítulo 3 — segunda versión"
No debería convertirse en un JSON gigante que replique toda la fila original.
5. Asociación
Cada entrada pertenece obligatoriamente a:
project_id
Esto simplifica:
RLS;
filtros;
consultas;
navegación;
agrupación por obra.
6. Cómo se generará
La actividad debe producirse en el momento de la acción real.
Ejemplo:
Admin
   ↓
UPDATE projects.status
   ↓
INSERT timeline(project_id, event, details)
No queremos:
Dashboard renderiza
   ↓
"parece que pasó algo"
   ↓
INSERT timeline
Eso sería incorrecto.
7. Dónde debería vivir la escritura
La escritura no debería estar repartida arbitrariamente por page.tsx.
El objetivo será concentrarla en los servicios que ya ejecutan la acción de negocio:
project.service
review.service
proposal.service
...
        ↓
activity/timeline helper
Podremos terminar con:
timeline.service.ts
pero solo si el patrón real del repo justifica ese servicio.
No quiero otro servicio vacío que simplemente envuelva .insert().
8. RLS
El modelo actual ya está bien encaminado:
Autor:
timeline.project_id
    ↓
projects.author_id = auth.uid()
Admin:
is_admin()
Esto ya existe en las políticas actuales. 
No necesitamos crear una segunda jerarquía de permisos.
9. Lectura
La consulta principal será conceptualmente:
timeline
WHERE project_id = currentProject
ORDER BY created_at DESC
La UI no necesita reconstruir el historial desde projects, reviews, proposals, etc.
Lee la proyección histórica.
10. No duplicar datos
Por ejemplo:
reviews.comment seguirá siendo la observación completa.
Timeline podría contener:
event = review_created
details = "Nuevo feedback en Capítulo 3"
No copiamos el comentario completo.
11. Relación con las seis fases
El cambio de fase nace de:
projects.status
Timeline conserva:
project_stage_changed
Por tanto:
projects.status = estado actual
timeline = historial
No invertimos esa relación.
12. Relación con production_stages
production_stages puede tener:
start_date
end_date
progress_percentage
status
assigned_to
Timeline no duplicará esos campos.
Solo registrará hitos importantes como:
production_stage_started
production_stage_completed
cuando realmente sean necesarios.
13. Relación con reviews
Actualmente reviews tiene:
deliverable_id
comment
status
created_at
y está conectada a deliverables → projects. 
Por tanto, al crear una review podríamos generar:
review_created
con contexto breve.
Cuando cambia:
open → resolved
podemos generar:
review_resolved
Pero Timeline no sustituye reviews.
14. Relación con propuestas
proposals está relacionada con project_requests, y projects.proposal_id apunta a la propuesta. 
Los eventos de propuesta entrarán en Timeline solo después de que definamos exactamente qué acciones son relevantes en 1B2.5.
No quiero que 1B2.4 invente reglas de Propuestas.
15. Relación con Comunicación
Igual:
message sent
no significa necesariamente:
timeline event
La definición exacta quedará en 1B2.2/implementación de Comunicación y se respetará aquí.
16. Datos actuales
La auditoría de Supabase encontró:
timeline = 0 filas
Así que no tenemos que migrar ni limpiar un historial existente.
Eso facilita muchísimo la implantación posterior.
17. ¿Necesitamos triggers?
No como requisito inicial.
Los triggers podrían parecer atractivos para garantizar consistencia, pero aquí introducirían otra capa de lógica difícil de mantener.
Prefiero:
acción de negocio
→ servicio
→ operación principal
→ registro de actividad
y pruebas explícitas.
Solo usaríamos trigger si posteriormente descubrimos un evento que debe registrarse independientemente de cualquier cliente.
18. Decisión técnica
Queda:
timeline reutiliza su esquema actual; projects, production_stages, reviews, proposals y Comunicación siguen siendo fuentes maestras; los servicios de negocio generan eventos explícitos y la UI solo consume la proyección histórica.

No hace falta una nueva tabla, ni una nueva arquitectura de eventos global, ni cambios de Supabase en esta etapa.
El siguiente paso es 1B2.4.4 — Reglas de comportamiento, donde definimos exactamente qué eventos se generan, cuándo, cómo evitamos duplicados y qué sucede cuando una acción falla a mitad de camino.
