# Diseño funcional de Notas internas — 1B2.6.2

Este documento define la experiencia funcional del módulo de Notas internas, garantizando su aislamiento respecto al autor y su integración operativa en el workspace del Admin.

## 1. Propósito
Espacio privado para el equipo de Studio Flamkit donde se registra información interna y recordatorios sobre un proyecto. **Nunca es visible para el autor ni se mezcla con otros módulos.**

## 2. Ubicación y Acceso
- **Workspace Admin**: Integrado dentro del contexto de cada proyecto.
- **Autor**: Sin visibilidad. No se muestra ninguna pestaña, aviso o icono en el Dashboard del autor.
- **Ubicación UI**: Bloque dedicado en el área de gestión de proyectos, evitando una página global aislada para mantener el contexto del proyecto.

## 3. Experiencia Visual
- **Identidad**: Tarjeta o sección etiquetada como "Notas internas" con un candado (🔒) para reforzar visualmente el concepto de privacidad (Solo equipo).
- **Contenido**: Lista cronológica (más recientes primero) que incluye: texto de la nota, nombre del autor (Admin), fecha de creación y acciones (Editar/Eliminar).

## 4. Flujo funcional
- **Crear**: Botón "+ Añadir nota" que despliega un editor sencillo para guardar la entrada.
- **Editar**: Acción simple sobre notas existentes, sin necesidad de historial de versiones en esta fase.
- **Eliminar**: Acción con confirmación previa.
- **Autor**: El sistema identifica automáticamente al Admin actual (vía sesión) como autor de la nota.

## 5. Integración y Separación
- **Feedback**: El feedback es editorial y visible al autor; las notas internas son privadas. No se mezclan.
- **Timeline**: No genera eventos de actividad pública. El Timeline es el historial público del proyecto; las notas son información de trabajo privado.
- **Comunicación**: No son un canal de chat con el autor.
- **Notificaciones**: No disparan avisos al autor.

## 6. Escalabilidad e Integridad
- La arquitectura permite extensiones futuras (etiquetas, búsquedas, adjuntos internos) sin modificar la estructura fundamental.
- **Privacidad**: La integridad se basa en RLS, no en ocultar componentes.

---

### Resultado de 1B2.6.2
**Notas internas será un bloque privado dentro del workspace de cada proyecto en Admin, con capacidades de crear, listar, editar y eliminar; nunca aparecerá en el entorno del Autor ni disparará eventos en módulos públicos.**

*El siguiente paso será **1B2.6.3 — Modelo técnico**, para aterrizar la implementación sobre la tabla `internal_notes` existente.*


1B2.6.2 — Diseño funcional
1. Propósito
Una nota interna sirve para que el equipo de Studio Flamkit deje información privada sobre un proyecto.
Ejemplos:
“El autor pidió mantener la portada actual.”

“Esperar confirmación del editor antes de avanzar.”

“Este proyecto requiere revisión especial del audio.”

No es feedback para el autor.
No es mensaje.
No es actividad.
2. Ubicación
La nota vivirá dentro del workspace del proyecto en Admin.
Conceptualmente:
Proyecto
├── Resumen
├── Capítulos
├── Entregables
├── Feedback
├── Actividad
└── Notas internas
No crearíamos una página global /admin/notas todavía.
La nota siempre tiene contexto de proyecto, y la interfaz debe respetar eso.
3. Diseño visual
Propongo una tarjeta lateral o bloque específico:
┌─────────────────────────────────┐
│ 🔒 Notas internas               │
│ Solo visible para el equipo     │
│                                 │
│ Ana — 10 ago                    │
│ “Esperar confirmación...”       │
│                                 │
│ Luis — 9 ago                    │
│ “El autor pidió...”             │
│                                 │
│ [+ Añadir nota]                 │
└─────────────────────────────────┘
La señal visual de privacidad es importante:
🔒 Solo equipo

Así nadie puede confundirlo con Feedback.
4. Crear nota
Botón:
+ Añadir nota
abre un editor pequeño:
Nueva nota interna

[ Escribe una nota... ]

[Cancelar] [Guardar nota]
Al guardar:
INSERT internal_notes
con el proyecto actualmente seleccionado.
5. Qué aparece en una nota
Cada tarjeta debe mostrar:
contenido;
nombre del autor de la nota;
fecha;
acciones administrativas.
Ejemplo:
Ana García · hace 2 h

“Confirmar si el capítulo 4
mantiene la versión enviada.”

[Editar] [Eliminar]
6. Orden
Las notas más recientes arriba.
created_at DESC
No debemos añadir otro campo de prioridad hasta que exista una necesidad real.
7. Edición
Admin puede editar una nota.
Pero visualmente conviene indicar:
editada

si posteriormente queremos transparencia interna.
La tabla actual no tiene updated_at.
Por tanto, para la primera versión:
podemos mantener edición simple sin inventar un sistema de historial de versiones.
La necesidad de historial de edición queda fuera.
8. Eliminación
Admin puede eliminar una nota desde:
[Eliminar]
con confirmación:
“¿Eliminar esta nota interna?”

Como la tabla ya tiene una política de eliminación para Admin, el backend está preparado. 
No necesitamos borrar en cascada desde la UI.
9. Estado vacío
Como actualmente hay cero notas reales:
Notas internas

Todavía no hay notas para este proyecto.

[+ Añadir nota]
No utilizar contenido ficticio.
10. Autor de la nota
El author_id existente representa quién creó la nota.
La UI debe mostrar el nombre real del administrador siempre que podamos resolverlo mediante authors.
No mostrar solamente el UUID.
11. Privacidad
La UI debe dejar claro:
Estas notas nunca son visibles para el autor de la obra.

Y esto no debe depender de esconder el componente.
La seguridad real sigue siendo RLS.
12. Relación con Feedback
No habrá un botón:
“Crear nota interna desde feedback”

en la primera versión.
¿Por qué?
Porque podría provocar que el equipo use notas internas para sustituir el feedback visible.
La separación será:
Feedback
→ algo que el autor debe ver

Nota interna
→ algo que el equipo necesita recordar
13. Relación con Actividad / Timeline
Crear una nota interna no genera automáticamente Timeline.
No tiene sentido mostrar al autor:
“Admin añadió una nota interna.”

porque revelaría indirectamente información privada.
Ni siquiera debe aparecer como evento público.
14. Relación con Notifications
No genera notificación al autor.
Puede eventualmente generar una señal interna para el equipo en una fase posterior, pero no forma parte de 1B2.6.
15. Relación con Comunicación
Una nota interna no abre un chat.
Si el equipo decide que el autor debe saber algo:
Nota interna
   ↓
acción explícita
   ↓
Feedback / Mensaje
Nunca se copia automáticamente.
16. Relación con Propuestas
Tampoco se añade una nota interna automáticamente al crear o rechazar una propuesta.
Admin puede escribirla manualmente:
“El autor está negociando el plazo.”

Pero permanece aislada.
17. Dashboard del autor
Nada.
No mostramos:
pestaña;
contador;
aviso;
resumen;
icono.
La ausencia es intencional.
18. Acceso Admin
Dentro del proyecto seleccionado:
Resumen
...
Notas internas
Todos los administradores autorizados pueden consultarlas según RLS.
La UI no debe implementar filtros de usuario como sustituto de permisos.
19. Escalabilidad
La primera versión será una lista sencilla.
Pero la estructura permite posteriormente añadir:
búsqueda;
etiquetas;
filtros por autor;
archivado;
historial de edición;
menciones internas;
adjuntos internos.
No se implementan ahora.
20. Responsive
En desktop:
Workspace
┌──────────────┬───────────────┐
│ contenido    │ notas internas│
└──────────────┴───────────────┘
En móvil:
Contenido

Notas internas
como sección apilada.
21. Diferencia con el resto del producto
Sistema	Público para autor	Propósito
Feedback	✅	Correcciones
Mensajes	✅	Conversación
Propuesta	✅	Oferta
Actividad	✅	Historial
Notificaciones	✅	Avisos
Internal Notes	❌	Trabajo interno


Eso debe mantenerse.
Resultado de 1B2.6.2
La decisión funcional queda:
Notas internas será un bloque privado dentro del workspace de cada proyecto en Admin, con crear, listar, editar y eliminar; nunca aparecerá en Dashboard, Feedback, Timeline, Notificaciones o Mensajes.

Y, a diferencia de Propuestas, aquí no necesitamos una nueva entidad de negocio. La tabla internal_notes ya es el núcleo correcto.
El siguiente paso es 1B2.6.3 — Modelo técnico, donde definimos exactamente cómo consultar, crear, editar y eliminar las notas y qué servicio/hook debería encargarse.
