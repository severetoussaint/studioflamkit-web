# Modelo técnico de Notas internas — 1B2.6.3

Este documento define la arquitectura técnica para la gestión de Notas internas, centralizando la lógica en el servicio de negocio y asegurando la consistencia con el modelo RLS existente.

## 1. Fuente de verdad y Esquema
- **Tabla**: `internal_notes` (ya existente).
- **Relaciones**: `project_id` vincula al proyecto; `author_id` vincula al autor de la nota (admin).
- **Privacidad**: RLS `is_admin()` garantiza que solo el equipo editorial pueda acceder o gestionar estas notas.
- **Sin cambios de esquema**: No se añadirán columnas (`updated_at`, `priority`, etc.) en esta fase para mantener la simplicidad.

## 2. Capa de Servicio (`internal-notes.service.ts`)
Responsabilidades centralizadas para operaciones de datos:
- `listInternalNotes(projectId)`: Consulta ordenada por fecha (`created_at DESC`).
- `createInternalNote(projectId, note)`: Inserción vinculando al Admin de la sesión actual (`auth.uid()`).
- `updateInternalNote(noteId, note)`: Edición de contenido.
- `deleteInternalNote(noteId)`: Eliminación.

## 3. Lógica de Negocio y Seguridad
- **Atribución**: La creación de la nota obtiene el ID del Admin desde el contexto de autenticación (`auth.uid()`), evitando inyección desde la UI.
- **Resolución de nombres**: El servicio o un mapper transformará el UUID del autor en su `full_name` para la UI.
- **RLS**: Se mantiene el acceso restringido a Admins, garantizando que el autor de la obra nunca vea este historial.

## 4. Arquitectura de Frontend
- **Hook de estado**: `useInternalNotes(projectId)` encapsula la lógica de carga, creación, edición, borrado y manejo de estados (loading, error).
- **Componentes**: 
    - `InternalNotesPanel`: Contenedor principal integrado en el workspace del Admin.
    - `InternalNoteCard`: Visualización de cada nota con autor, fecha y acciones.
    - `InternalNoteEditor`: Formulario de creación/edición.
- **Estado de UI**: La gestión de ediciones o notas nuevas se mantiene como estado local, minimizando la duplicación de datos con Supabase.

## 5. Integración y Comportamiento
- **Independencia**: No se dispara ningún evento de `Timeline` ni `Notifications` al crear/editar/eliminar una nota. Son procesos privados.
- **Relación con otros módulos**: No hay enlace directo ni copia de datos hacia `reviews`, `mensajes` o `propuestas`.
- **Estado Vacío**: Se gestionará explícitamente ("Todavía no hay notas") sin inyectar datos ficticios.
- **Atomicidad**: Cada operación de escritura debe ser completa y verificable.

## 6. Decisión final técnica
Se reutiliza la tabla `internal_notes` sin modificaciones en el esquema. La arquitectura se basa en:
1. **Servicio** (Acceso a Supabase).
2. **Hook** (Gestión de estado y operaciones).
3. **Componentes UI** (Presentación aislada del contexto de proyectos).

Vamos con 1B2.6.3 — Modelo técnico de Notas internas.
La decisión central es conservar la tabla existente y construir una capa fina encima, sin convertir internal_notes en otro sistema paralelo.
1B2.6.3 — Modelo técnico
1. Fuente de verdad
La fuente maestra será:
internal_notes
Su contexto viene de:
internal_notes.project_id
        ↓
projects.id
Y la identidad del creador:
internal_notes.author_id
        ↓
authors.id
No habrá otra tabla de notas.
2. Esquema que reutilizamos
Tal como existe actualmente:
id
project_id
note
author_id
created_at
No necesitamos añadir para esta fase:
updated_at
status
priority
category
archived
is_pinned
La primera versión debe ser simple.
3. Qué significa author_id
Aquí author_id no representa al autor de la obra.
Representa al usuario que creó la nota interna.
Por eso la UI tendrá que resolver:
internal_notes.author_id
        ↓
authors.full_name
y mostrar el nombre, no el UUID.
4. Servicio
La lógica debe quedar fuera de admin/page.tsx.
Propongo:
src/services/internal-notes.service.ts
o el naming equivalente que ya use el repo.
API mínima:
listInternalNotes(projectId)
createInternalNote(projectId, note)
updateInternalNote(noteId, note)
deleteInternalNote(noteId)
Nada de lógica visual dentro del servicio.
5. Resolver el usuario actual
Al crear una nota:
current admin
      ↓
auth.uid()
      ↓
author_id
No aceptar author_id arbitrario desde el formulario.
La identidad debe derivarse de la sesión autenticada.
Esto evita que un Admin cree notas falsamente atribuidas a otro usuario.
6. Creación
La operación conceptual:
createInternalNote(projectId, note)
          ↓
INSERT internal_notes
Datos:
{
  project_id: projectId,
  note: note.trim(),
  author_id: currentUser.id
}
created_at queda a cargo de la base si tiene default.
7. Consulta
La función:
listInternalNotes(projectId)
deberá devolver:
{
  id,
  projectId,
  note,
  authorId,
  authorName,
  createdAt
}
La transformación a authorName puede ocurrir en el servicio o en un mapper de datos.
La UI no debería saber cómo hacer el join.
8. Orden
La consulta será:
.eq('project_id', projectId)
.order('created_at', { ascending: false })
Últimas notas arriba.
9. Edición
La edición debe ser:
UPDATE internal_notes
SET note = ...
WHERE id = ...
No podemos permitir editar:
project_id;
author_id;
created_at.
Esto es importante porque son metadatos estructurales.
10. Quién puede editar
RLS ya establece:
is_admin()
como condición de acceso.
Por tanto:
Solo Admin puede modificar notas.

La UI puede filtrar, pero la seguridad real está en Supabase.
11. ¿Puede un Admin editar una nota creada por otro Admin?
Con la política actual:
is_admin()
sí.
Eso es consistente con que las notas pertenecen al equipo, no a un individuo.
No vamos a restringirlas al creador.
12. Eliminación
La eliminación:
deleteInternalNote(noteId)
estará protegida por la política Admin correspondiente.
La UI deberá pedir confirmación.
No habrá borrado automático por antigüedad.
13. RLS actual
La auditoría confirmó:
internal_notes_admin_only
USING is_admin()
WITH CHECK is_admin()
y una política de delete para Admin. 
Así que la arquitectura de permisos ya coincide con el diseño.
No necesitamos abrir RLS para el autor. 
14. ¿Hook?
Sí, aquí tiene sentido un hook pequeño porque la nota es una pieza de estado local del workspace:
useInternalNotes(projectId)
Responsabilidades:
cargar;
crear;
editar;
eliminar;
loading;
error;
refresh.
Pero no debe contener reglas de permisos.
15. UI consume el hook
La estructura sería:
AdminProjectWorkspace
       ↓
useInternalNotes(projectId)
       ↓
InternalNotesPanel
Esto evita meter consultas Supabase dentro del componente visual.
16. Componentes
Modelo recomendado:
src/components/admin/internal-notes/
con:
InternalNotesPanel
InternalNoteCard
InternalNoteEditor
No necesitamos un sistema de componentes gigantesco.
17. Modelo de datos UI
interface InternalNoteViewModel {
  id: string;
  projectId: string;
  note: string;
  authorId: string | null;
  authorName: string;
  createdAt: string;
}
Si author_id no pudiera resolverse por alguna razón, la UI puede mostrar:
Equipo editorial

en lugar de romperse.
18. Estado de edición
El componente puede tener localmente:
editingNoteId
draftText
isSaving
Eso es estado de UI.
No duplicamos el contenido persistido en otro store.
19. Estado de carga
Debe existir:
Loading
Empty
Loaded
Error
Ejemplo:
Cargando notas…
y:
No hay notas internas para este proyecto.
20. Relación con projects
La consulta siempre estará limitada al proyecto actual.
No hacer:
SELECT * FROM internal_notes
para luego filtrar en React.
Debe filtrar en Supabase:
project_id = selectedProjectId
Esto es mejor para:
seguridad;
rendimiento;
claridad.
21. No usar Timeline
Una creación/edición de nota no ejecuta:
insert timeline
porque esa actividad es privada.
22. No usar Notifications
Tampoco:
insert notifications
para el autor.
La nota es completamente interna.
23. No usar Communication
No crear conversaciones desde las notas.
Si un contenido debe llegar al autor, el Admin debe realizar una acción explícita en:
Feedback;
Mensajes;
Propuesta;
según corresponda.
24. Auditoría técnica
internal_notes y audit_logs son distintos.
internal_notes
= contexto operativo privado

audit_logs
= trazabilidad técnica/administrativa
No copiar una nota a audit_logs automáticamente.
25. Eliminación de proyecto
Como internal_notes.project_id depende de projects, antes de implementar delete de proyectos habrá que confirmar el comportamiento FK/cascade actual.
La UI de Admin ya tiene eliminación de proyectos, así que esto es una comprobación importante para no dejar referencias huérfanas.
No vamos a cambiarlo en 1B2.6.
26. Datos existentes
Actualmente:
internal_notes = 0
No hay migración de datos.
La implementación debe funcionar igualmente para proyectos futuros y para un proyecto ya existente sin notas.
27. Rango de responsabilidades
Servicio
Supabase + transformaciones.
Hook
Estado y operaciones del componente.
Componentes
Presentación.
Admin page
Orquestación del proyecto seleccionado.
Queda así:
Admin Page
   ↓
useInternalNotes
   ↓
internal-notes.service
   ↓
Supabase
28. Decisión técnica final
No se modifica el modelo de Supabase para 1B2.6.3.
Reutilizamos:
internal_notes
y construimos únicamente:
internal-notes.service
useInternalNotes
InternalNotesPanel
InternalNoteCard
InternalNoteEditor
con RLS Admin-only.
Con esto, el modelo técnico queda alineado con la tabla existente y con la arquitectura que ya definimos para Feedback, Timeline, Propuestas y Comunicación.
El siguiente paso es 1B2.6.4 — Reglas de comportamiento, donde cerramos edición, eliminación, privacidad, atribución, estados vacíos y límites de uso.
