# Especificación de implementación — 1B2.6.5

Este documento define el contrato técnico para la implementación del módulo de Notas internas, utilizando la infraestructura existente en Supabase y integrándolo exclusivamente en el workspace del Admin.

## 1. Persistencia y Estructura
- **Reutilización**: Se utiliza la tabla `internal_notes` existente sin modificaciones.
- **Relación**: Asociada obligatoriamente a un `project_id`.
- **Sin cambios de esquema**: No se requieren campos adicionales (`updated_at`, `priority`, etc.) en esta fase para mantener la simplicidad.

## 2. Capa de Servicio (`internal-notes.service.ts`)
- **API**: `listInternalNotes(projectId)`, `createInternalNote(projectId, note)`, `updateInternalNote(noteId, note)`, `deleteInternalNote(noteId)`.
- **Identidad**: El `author_id` se extrae del contexto de autenticación (`auth.uid()`).
- **Transformación**: El servicio resuelve el `authorName` a partir del UUID, devolviendo objetos preparados para la UI.

## 3. Lógica de UI (Hook `useInternalNotes.ts`)
- **Gestión de estado**: Encapsula carga, mutaciones (crear/editar/borrar) y estados de carga/error.
- **Deduplicación**: Operaciones protegidas para evitar envíos dobles.
- **Actualización**: La UI se refresca tras confirmación exitosa del servidor, sin simulaciones optimistas riesgosas.

## 4. Componentes UI
- **`InternalNotesPanel`**: Contenedor central. Gestiona el layout del bloque y muestra estados (cargando, vacío, con notas).
- **`InternalNoteCard`**: Visualización individual con metadatos (autor, fecha) y acciones (Editar/Eliminar).
- **`InternalNoteEditor`**: Formulario integrado para entrada de texto, con validación de contenido no vacío.

## 5. Reglas de Integración y Seguridad
- **Privacidad**: El autor de la obra no tiene visibilidad ni acceso. La seguridad es impuesta por RLS (`is_admin()`).
- **Contexto**: Las notas cambian automáticamente al cambiar el proyecto seleccionado en el Admin. No existe un estado global de notas.
- **Separación de responsabilidades**:
    - No se genera actividad en `timeline`.
    - No hay integración con `notifications`.
    - No se mezclan con `Feedback editorial` (`reviews`).

## 6. Pruebas Funcionales
- **CRUD**: Creación, edición y eliminación validada contra Supabase.
- **Integridad**: Comprobación de que una nota siempre está vinculada al proyecto correcto.
- **Seguridad**: Verificación de que el autor de la obra no puede acceder a estas notas (RLS).
- **Concurrencia**: Validación de que cambios en un proyecto no se filtran a otros.

## 7. Orden de Implementación
1. Implementar `internal-notes.service.ts`.
2. Crear `useInternalNotes.ts`.
3. Desarrollar componentes (`Panel`, `Card`, `Editor`).
4. Integración en el workspace de proyectos del Admin.
5. Pruebas de CRUD, RLS y sincronización de proyecto.
6. Verificación de regresiones en funcionalidades existentes.
7. Linting y Build final.
