# Reglas de comportamiento de Notas internas — 1B2.6.4

Este documento establece las reglas de negocio para el módulo de Notas internas, garantizando su privacidad, integridad y comportamiento frente a acciones del usuario o errores técnicos.

## 1. Principio fundamental
Una nota interna es **información operativa privada del equipo** asociada exclusivamente a un proyecto. No es Feedback, Mensaje, Notificación, Actividad ni Propuesta.

## 2. Creación y Contenido
- **Acción**: Solo Admin autorizado.
- **Contexto**: Obligatoriamente vinculada a un `project_id`. El botón "Añadir nota" solo existe dentro del contexto de proyecto.
- **Atribución**: `author_id` se deriva automáticamente de la sesión autenticada.
- **Validación**: El contenido debe ser texto no vacío (tras `trim`).

## 3. Visibilidad y Privacidad
- **Admin**: Acceso total (consulta, edición, eliminación).
- **Autor**: Visibilidad nula. No hay pestañas, contadores ni avisos en el Dashboard. La seguridad recae sobre RLS.
- **Independencia**: No se generan automáticamente ni son visibles en Feedback, Timeline, Notificaciones o Mensajes.

## 4. Gestión de Edición y Eliminación
- **Edición**: Admin puede editar cualquier nota. No existe historial de versiones en la primera versión.
- **Eliminación**: Explícita mediante botón con confirmación previa.
- **Protección**: No se permite editar metadatos estructurales (`project_id`, `author_id`, `created_at`).

## 5. Comportamiento frente a fallos
- **Atomicidad**: Las operaciones deben confirmarse contra Supabase antes de actualizar la UI. Si una operación falla, se mantiene el estado anterior y se muestra un mensaje de error.
- **Deduplicación**: La UI bloqueará el botón de acción mientras una operación esté en curso para evitar duplicados accidentales.
- **Integridad**: No deben existir estados inconsistentes (ej: "Nota guardada" sin confirmación del servidor).

## 6. Integración Funcional
- **Sin efectos secundarios**: Crear, editar o borrar una nota **no dispara** eventos en Timeline, Notificaciones ni altera estados de proyectos, entregables o rutas editoriales.
- **Cambio de Proyecto**: La lista de notas se limpia y recarga instantáneamente al cambiar el `projectId` activo.
- **Estado vacío**: Se muestra un mensaje explícito ("Todavía no hay notas") sin inyectar datos ficticios.
- **Seguridad**: RLS centralizado en Supabase impide acceso no autorizado, independientemente de la lógica de interfaz.

## 7. Diseño de Interacción
- **Orden**: Las notas más recientes siempre aparecen primero (`created_at DESC`).
- **Seguridad visual**: Tarjetas identificadas con el icono de candado (🔒) para reforzar el concepto de privacidad dentro del entorno Admin.
- **Responsividad**: Adaptación vertical en móvil y disposición lateral en desktop.

---
### Decisión final cerrada
Las notas internas funcionan como un **log privado de trabajo** sin efectos colaterales públicos. Se garantiza la privacidad total del autor mediante RLS y una clara separación de responsabilidades: 
`Notas internas` (Privado) ≠ `Feedback`/`Comunicación` (Público/Compartido).

Vamos con 1B2.6.4 — Reglas de comportamiento de Notas internas.
Aquí dejamos cerradas las reglas para que la implementación no tenga que improvisar.
1. Regla principal
Una nota interna es:
información operativa privada del equipo asociada a un proyecto.

No es feedback, mensaje, notificación, actividad ni propuesta.
2. Crear nota
Solo un Admin autorizado puede crearla.
Flujo:
Proyecto seleccionado
      ↓
+ Añadir nota
      ↓
escribir contenido
      ↓
Guardar
      ↓
internal_notes
No se crea una nota vacía.
3. Contenido obligatorio
La nota debe contener texto no vacío después de hacer trim.
Ejemplo inválido:
"     "
No se guarda.
4. Proyecto obligatorio
Toda nota pertenece a un project_id.
No existe:
nota global
por tanto, el botón Añadir nota solo existe dentro del contexto de un proyecto.
5. Autor de la nota
author_id se obtiene de la sesión autenticada.
Nunca:
form.author_id
La identidad la determina el sistema.
Así la atribución es confiable.
6. Visibilidad
Las notas son 100 % privadas para Admin.
El autor de la obra:
no puede leerlas;
no puede editarlas;
no puede eliminarlas;
no recibe notificación;
no las ve en Timeline.
La seguridad no depende de ocultar el componente; depende de RLS.
7. Lectura
Las notas se muestran únicamente del proyecto seleccionado:
selectedProjectId
      ↓
internal_notes.project_id
No cargar notas de todos los proyectos para después filtrarlas en React.
8. Orden
Las más recientes primero:
created_at DESC
La actividad histórica de Timeline sigue siendo independiente.
9. Editar
Un Admin puede editar cualquier nota del equipo.
Al editar:
cambia note;
no cambia project_id;
no cambia author_id;
no cambia created_at.
No convertiremos la edición en una nueva nota.
10. Historial de edición
La primera versión no conserva historial de versiones.
Por tanto:
nota original
   ↓
UPDATE
   ↓
nota actual
Si más adelante necesitamos auditoría de cambios, será una capacidad distinta.
11. Eliminar
Un Admin puede eliminar una nota.
La UI debe pedir confirmación:
“¿Eliminar esta nota interna?”

La eliminación es explícita.
No existe auto-delete por antigüedad.
12. No borrar silenciosamente
Después de eliminar, la lista debe actualizarse desde el resultado real de Supabase.
No quitar visualmente la tarjeta y asumir que funcionó.
13. Fallos de creación
Si INSERT falla:
nota sigue en editor
+
mensaje de error
No mostrar:
“Nota guardada”

hasta recibir confirmación real.
14. Fallos de edición
Si UPDATE falla:
conservar el contenido que estaba persistido;
mostrar error;
no sobrescribir silenciosamente el estado local con la versión fallida.
15. Fallos de eliminación
Si DELETE falla:
la nota sigue visible;
mostrar error;
no simular que desapareció.
16. Doble envío
Si Admin pulsa dos veces Guardar:
Guardar
Guardar
no deben aparecer dos notas accidentalmente por un doble submit de UI.
La UI debe bloquear la acción durante la operación.
17. No duplicar por refresh
Recargar la página no debe crear notas.
Las notas solo nacen de una operación explícita de creación.
18. No generar Timeline
Crear, editar o eliminar una nota:
NO genera:
timeline event
Porque revelar que hubo una nota interna podría filtrar información privada.
19. No generar Notification
Tampoco genera:
notification → autor
Una nota interna es deliberadamente silenciosa hacia el autor.
20. No generar mensaje
Una nota no abre una conversación.
Si Admin necesita comunicar algo al autor, debe hacerlo deliberadamente desde:
Mensajes;
Feedback;
Propuesta.
21. No modificar estado del proyecto
Crear una nota nunca cambia:
projects.status
Ni:
production_stages.status
22. No modificar Feedback
Una nota interna no puede:
resolver una review;
crear feedback;
modificar una review.
Son entidades separadas.
23. No modificar Propuesta
Tampoco puede cambiar:
amount;
services;
deadline;
proposal.status.
Una nota es contexto interno.
24. Proyecto eliminado
Si se elimina un proyecto, la implementación debe respetar la relación FK existente.
No se debe intentar resolver esto desde React.
La regla funcional:
una nota interna nunca puede sobrevivir como nota huérfana de un proyecto eliminado.

25. Proyecto seleccionado cambia
Cuando Admin cambia de proyecto:
Proyecto A
   ↓
Proyecto B
las notas deben cambiar a las de B.
No conservar temporalmente las notas de A como si pertenecieran a B.
26. Estado vacío
Si no existen notas:
🔒 Notas internas

Todavía no hay notas para este proyecto.

[+ Añadir nota]
Sin datos ficticios.
27. Error de permisos
Si el usuario deja de ser Admin o la RLS rechaza la operación:
la operación falla.

No se intenta hacer fallback con una consulta insegura ni con una ruta alternativa.
28. Escapado/renderizado
El contenido debe mostrarse como texto seguro.
No interpretar el contenido de la nota como HTML arbitrario.
29. Longitud
La primera versión debería imponer un límite razonable de texto para evitar notas gigantes, pero ese límite debe corresponder a una necesidad real y no a una restricción arbitraria de la base.
La UI puede mostrar textarea con contador posteriormente.
No añadimos todavía metadata de longitud.
30. Móvil
En móvil:
Notas internas
   ↓
lista vertical
   ↓
editor
Sin modal innecesario si una sección inline resulta suficiente.
Decisión cerrada de 1B2.6.4
Las notas internas quedan definidas como:
PRIVADAS
POR PROYECTO
CREADAS EXPLÍCITAMENTE
EDITABLES POR ADMIN
ELIMINABLES POR ADMIN
SIN EFECTOS SECUNDARIOS PÚBLICOS
Y mantienen estas fronteras:
Notas internas ≠ Feedback
Notas internas ≠ Mensajes
Notas internas ≠ Timeline
Notas internas ≠ Notifications
Notas internas ≠ Propuestas
