# Auditoría de 1B2.5 — Gestión de Propuestas

Esta auditoría cruza la arquitectura del repositorio con el modelo de datos existente en Supabase, revelando una discrepancia crítica entre el flujo real operativo y la infraestructura de propuestas disponible.

## 1. El estado real: Discrepancia modelo vs. operativo
Existe una infraestructura completa en Supabase (tablas `proposals`, `evaluations`, `project_requests`) que no está siendo utilizada por el flujo operativo actual.

- **Flujo actual**: `project_requests` -> `projects` (con cálculo de cotización manual en UI).
- **Modelo deseado (preparado en DB)**: `project_requests` -> `evaluations` -> `proposals` -> `projects`.
- **Dato clave**: El proyecto activo actual en `production` tiene `proposal_id = null`, confirmando que el flujo de propuestas persistidas está desconectado.

## 3. Puntos de conflicto
- **Fragmentación de estados**: Existen al menos tres modelos de estado conflictivos (`project_requests`, `proposals`, UI Admin).
- **Inconsistencia de fuente de verdad**: La UI calcula cotizaciones basándose en el manuscrito, ignorando la tabla `proposals`.
- **Desconexión Autor-Admin**: El autor no tiene una experiencia de revisión de propuestas. Todo el proceso es puramente administrativo.

## 4. Conclusión operativa
La tabla `proposals` no está participando en el flujo real. Tenemos una "UI de cotización" que desemboca directamente en la creación de proyectos sin generar una propuesta formal (persistencia en DB). La seguridad (RLS) ya está preparada, pero la lógica de negocio y la experiencia de usuario están desconectadas.

## 5. Qué deja claro esta auditoría
`1B2.5` no es una fase para "crear" propuestas, sino para **reconciliar el flujo comercial actual con el modelo de datos disponible**. Debemos definir si la cotización actual debe transformarse en una `proposal` persistente y cómo integrar al autor en el proceso de revisión y aceptación.
