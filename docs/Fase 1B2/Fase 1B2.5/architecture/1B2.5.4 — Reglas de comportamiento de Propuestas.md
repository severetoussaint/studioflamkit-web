# Reglas de comportamiento de Propuestas — 1B2.5.4

Este documento define la lógica de negocio para el ciclo de vida de las propuestas, asegurando la integridad de los datos, la separación de conceptos y la trazabilidad del proceso comercial.

## 1. Ciclo de Vida
El estado de la propuesta es unidireccional y final:
`pending` → (`accepted` | `rejected` | `expired`).
- Una propuesta aceptada, rechazada o expirada es inmutable. 
- Cualquier renegociación comercial implica la creación de una nueva propuesta, preservando el historial.

## 2. Definición de Estados
- **`pending`**: Propuesta activa disponible para la decisión del autor. Es el único estado en el que el autor puede interactuar (Aceptar/Rechazar).
- **`accepted`**: Oferta formal aceptada. Vincula el proyecto mediante `projects.proposal_id`.
- **`rejected`**: Oferta rechazada. No genera proyecto.
- **`expired`**: Oferta cuya fecha de validez (`expires_at`) ha sido superada.

## 3. Flujo de Negocio
1. **Creación**: Admin crea la propuesta basada en una evaluación (`evaluations`). La propuesta nace en estado `pending`.
2. **Envío**: Admin formaliza la disponibilidad de la propuesta para el autor (acción distinta a la creación).
3. **Decisión del Autor**:
    - **Aceptación**: Activa el proyecto y enlaza `projects.proposal_id`. Debe ser una operación atómica.
    - **Rechazo**: Transición a `rejected`. Se permite opcionalmente un motivo.
4. **Expiración**: Evaluada en el momento de la consulta o intento de aceptación.

## 4. Integridad y Seguridad
- **Fuente de verdad**: La tabla `proposals` es la única fuente de condiciones comerciales (monto, servicios, plazos). No se duplica información en `projects`.
- **Deduplicación**: Operaciones como `acceptProposal` deben ser idempotentes. Una propuesta aceptada no puede crear un segundo proyecto.
- **RLS**: Implementación estricta para garantizar que el autor solo vea/decida sobre propuestas vinculadas a sus solicitudes, y que Admin mantenga el control administrativo.

## 5. Integración con otros módulos
- **Comunicación**: Las discusiones sobre propuestas ocurren en el motor de Mensajes (1B2.2), no dentro de la entidad `proposals`.
- **Notificaciones**: Eventos de creación, aceptación y rechazo disparan avisos al usuario correspondiente.
- **Timeline**: Registro de hitos (`proposal_created`, `proposal_accepted`, etc.) como fuente histórica.
- **Internal Notes**: Utilizadas por Admin para justificaciones internas, sin exponerse al autor.
- **Proyectos**: La activación del proyecto no salta fases de la Ruta Editorial.

## 6. Reglas de Validación
- No se permiten propuestas incompletas (`amount < 0`, servicios vacíos).
- La aceptación solo es válida si `proposal.status == pending` y `expires_at` es válido.
- No se permiten ediciones retroactivas sobre propuestas aceptadas (inmutabilidad).

### Resultado de 1B2.5.4
La lógica queda establecida: **La propuesta es la oferta formal derivada de una solicitud; su aceptación formaliza el proyecto manteniendo una trazabilidad limpia entre entidades.**

*El siguiente y último paso es **1B2.5.5 — Especificación de implementación** (UI, servicios, componentes y estrategia de despliegue).*


Vamos con 1B2.5.4 — Reglas de comportamiento de Propuestas.
Aquí cerramos las transiciones antes de escribir la especificación.
1. Ciclo de vida
El ciclo visible de una propuesta será:
pending
  ├──→ accepted
  ├──→ rejected
  └──→ expired
No hay vuelta atrás.
Una propuesta aceptada no vuelve a pending.
Una rechazada no se reactiva.
Una expirada tampoco vuelve a ser válida.
2. Qué significa pending
pending significa:
La propuesta está activa y espera una decisión del autor.

No significa “borrador”.
Por eso, en la primera versión, solo mostramos propuestas que ya están disponibles para el autor como pending.
Admin no necesita un estado persistente adicional para guardar un borrador hasta que demostremos que realmente lo necesita.
3. Crear propuesta
Crear una propuesta significa:
project_request existente
        ↓
proposal creada
        ↓
status = pending
Pero todavía no debe crearse el proyecto.
4. Enviar propuesta
Como el modelo actual no tiene sent_at ni draft, la primera versión tratará:
propuesta creada y validada = propuesta disponible para el autor

La acción de Admin será explícita:
[Crear propuesta]
        ↓
[Enviar al autor]
Aunque ambos pasos puedan terminar creando una sola fila proposals, la UI debe diferenciarlos para evitar que Admin envíe accidentalmente algo incompleto.
5. Validación antes de enviar
Antes de dejar una propuesta disponible para el autor:
request_id debe existir;
la solicitud debe ser válida;
amount debe ser ≥ 0;
los servicios deben tener contenido coherente;
revisions_included debe ser válido;
el plazo debe estar definido cuando el servicio lo requiera;
la expiración, si existe, debe ser futura.
No se debe permitir una propuesta incompleta.
6. Aceptación
Una aceptación válida requiere:
proposal.status === pending
y además:
proposal no ha expirado
Después:
pending → accepted
Y la aceptación debe producir exactamente una activación de proyecto.
7. Rechazo
El autor puede rechazar una propuesta pending.
Resultado:
pending → rejected
No se crea proyecto.
Puede registrarse opcionalmente un motivo, pero no añadiremos todavía una columna solo para eso si Comunicación puede cubrir la explicación.
8. Expiración
Si:
expires_at < now()
la propuesta deja de ser aceptable.
Resultado lógico:
pending → expired
La aplicación no debe permitir aceptar una propuesta que ya está vencida aunque la UI todavía tenga información antigua cargada.
La validación de expiración debe ocurrir en la operación de aceptación.
9. Expiración persistente
No necesitamos un cron para que el concepto sea seguro.
Puede ocurrir:
UI intenta aceptar
   ↓
comprueba expires_at
   ↓
detecta vencimiento
   ↓
marca expired
   ↓
rechaza la aceptación
Más adelante podríamos tener una tarea periódica para limpiar estados, pero no es requisito de la primera integración.
10. Aceptar y crear proyecto
La aceptación no debe hacer:
UPDATE proposal
INSERT project
desde dos lugares independientes con riesgo de doble ejecución.
El flujo debe comportarse como una operación de dominio:
acceptProposal()
    ↓
validar propuesta
    ↓
accepted
    ↓
crear/activar proyecto
    ↓
link proposal_id
Si el proyecto ya existe, no se crea otro.
11. Idempotencia
Si el usuario pulsa dos veces:
Aceptar
Aceptar
el sistema debe terminar con:
1 propuesta accepted
1 proyecto
no:
1 propuesta
2 proyectos
Esta es una prueba obligatoria.
12. Proyecto ya existente
Antes de crear:
projects
WHERE proposal_id = proposal.id
si ya existe:
reutilizar la asociación y no duplicar el proyecto.

También habrá que comprobar la posibilidad de que ya exista un proyecto para el mismo manuscript_id.
Ese conflicto debe provocar una protección explícita, no una segunda creación silenciosa.
13. Solicitud al aceptar
Cuando la propuesta es aceptada, project_requests.status debe quedar coherente con el resultado.
La transición prevista es:
evaluating → accepted
o el estado equivalente que esté usando realmente el servicio.
La implementación deberá usar una única transición oficial, no inventar un segundo estado.
14. Solicitud al rechazar
Si el autor rechaza:
proposal.status = rejected
la solicitud debe reflejar que ya no continúa por esa propuesta.
No debemos cerrar o cancelar automáticamente la solicitud si el negocio contempla que Admin pueda generar otra propuesta.
Eso es importante.
Por tanto:
rechazar una propuesta no necesariamente significa cancelar la solicitud original.

Esta distinción permite renegociar después sin romper el modelo.
15. Nueva propuesta para la misma solicitud
El diseño debe permitir potencialmente:
Request
 ├── Proposal A → rejected
 └── Proposal B → pending
Esto es una razón adicional para no convertir project_requests en la propuesta.
La tabla proposals permite mantener el historial de ofertas.
La regla será:
Solo una propuesta puede estar activa/aceptable para una solicitud a la vez.

16. Qué pasa con la propuesta anterior
Si se crea una nueva propuesta:
Proposal A = rejected
Proposal B = pending
No borramos A.
El historial permanece.
17. Notificaciones
Nueva propuesta
Autor recibe:
Nueva propuesta disponible

Aceptación
Admin recibe:
El autor aceptó la propuesta

Rechazo
Admin recibe:
El autor rechazó la propuesta

Expiración
Puede notificarse al autor y/o Admin según la política de producto que definamos, pero no es obligatorio generar ruido en la primera versión.
18. Timeline
Los eventos importantes serán:
proposal_created
proposal_accepted
proposal_rejected
proposal_expired
La regla es la misma de 1B2.4:
Primero ocurre y persiste el evento de negocio; después se registra la actividad.

No se genera Timeline desde la notificación.
19. Comunicación
La conversación es opcional.
Una propuesta puede existir sin conversación.
Y una conversación puede existir sin modificar la propuesta.
Ejemplo:
Proposal:
$1,200 · 30 días

Conversation:
"¿El plazo cuenta desde la entrega del manuscrito final?"
El chat no altera automáticamente:
monto;
servicios;
revisiones;
deadline.
Para cambiar una condición hace falta una nueva propuesta o una acción administrativa formal.
20. Condiciones aceptadas
Al aceptar, la propuesta representa las condiciones aceptadas.
Por eso:
no se debe modificar una propuesta accepted.

Si hay un cambio comercial posterior:
Proposal A = accepted
       ↓
nueva negociación
       ↓
Proposal B
Eso preserva el historial.
21. Notas internas
Admin puede registrar razonamientos internos en:
internal_notes
pero esos textos jamás pasan automáticamente a la propuesta que ve el autor.
Separación:
internal_notes
= interno

proposals
= oferta visible
22. Evaluación
La evaluación sigue siendo interna.
Su resultado puede utilizarse para construir la propuesta.
Pero:
evaluation.result = approved_with_notes
no significa automáticamente:
proposal.status = pending
La propuesta solo existe cuando Admin la crea explícitamente.
23. Ruta editorial
Aceptar una propuesta puede activar el proyecto, pero no debe directamente saltarse o manipular las seis fases editoriales.
La secuencia correcta es:
propuesta aceptada
       ↓
proyecto activado
       ↓
Ruta editorial empieza/continúa
No:
propuesta aceptada
       ↓
proyecto → completado
24. Error en aceptación
Si falla la creación/activación del proyecto:
no debemos dejar al autor viendo “Aceptada” si el sistema no pudo completar la activación de forma consistente.

La implementación debe tratar esto como una operación atómica o compensable.
El objetivo:
accepted + project linked
o un estado claramente recuperable.
Nunca:
accepted
pero sin proyecto
sin que el sistema sepa que existe ese caso.
25. UI durante acciones
Mientras se procesa:
Aceptar propuesta…
se deshabilita el botón para evitar doble envío.
Pero esto es solo UX.
La protección real debe existir en la lógica de negocio y Supabase.
26. Acceso del autor
El autor:
puede leer sus propuestas;
puede aceptar pending;
puede rechazar pending;
no puede modificar monto, servicios, deadline ni request_id.
Eso debe estar respaldado por RLS, no solo por la interfaz.
27. Acceso de Admin
Admin:
puede crear;
puede actualizar;
puede enviar;
puede consultar;
puede generar una nueva propuesta;
no debería modificar retroactivamente una propuesta aceptada.
28. Regla de historial
Nunca hacemos:
UPDATE amount = 1500
después de que fue aceptada.
La oferta aceptada debe permanecer como registro histórico.
Decisión cerrada de 1B2.5.4
El flujo final queda:
Solicitud
   ↓
Evaluación
   ↓
Crear propuesta
   ↓
pending
   │
   ├── aceptar ──→ accepted ──→ proyecto
   │
   ├── rechazar → rejected
   │
   └── expirar ─→ expired
Y se mantienen separados:
Proposal     = oferta formal
Project      = trabajo activado
Timeline     = historial
Notification = aviso
Communication = conversación
Internal Note = privado
Con esto 1B2.5.1 → 1B2.5.4 quedan cerradas.
El último paso de esta rama es 1B2.5.5 — Especificación de implementación.
