Perfecto. Pasamos a **1B2.2.3 — Modelo técnico de Comunicación**.

Aquí traducimos el diseño aprobado a arquitectura concreta. **Todavía no implementamos.**

## 1B2.2.3 — Modelo técnico

### 1. Nueva infraestructura necesaria
A diferencia de Notificaciones, aquí sí necesitamos persistencia nueva porque la auditoría confirmó que **no existe `messages` ni `conversations`**.

Propongo dos entidades principales:

```
conversations
├── id
├── author_id
├── project_id        nullable
├── type
├── subject
├── status
├── created_at
└── updated_at

messages
├── id
├── conversation_id
├── sender_type
├── sender_id
├── body
├── created_at
└── read_at
```
No crearíamos una tabla diferente para cada tipo de comunicación.

---

### 2. Por qué dos tablas
Porque necesitamos separar:

**la conversación**

de:

**los mensajes dentro de ella.**

Así podemos tener:

```
Conversación
"Consulta sobre mi novela"

   ├── Mensaje 1
   ├── Mensaje 2
   ├── Mensaje 3
   └── Mensaje 4
```
Esto permite crecer sin rehacer la arquitectura.

---

### 3. `author_id`
Toda conversación iniciada desde el lado del autor tendrá un `author_id`.

Esto permite aplicar RLS de forma sencilla:

> El autor solamente puede acceder a conversaciones donde `author_id = su propio author.id`.

---

### 4. `project_id`
Será **nullable**.

Esto es importante.

Podemos tener:

```
Conversación sobre Mi novela
→ project_id = X
```
pero también:

```
Consulta general de cuenta
→ project_id = null
```
Así no obligamos artificialmente todas las conversaciones a pertenecer a una obra.

---

### 5. `type`
Propongo:

```
general
project
editorial
proposal
support
```
No necesitamos crear cinco tablas.

Es simplemente una clasificación.

---

### 6. `subject`
La conversación necesita un asunto.

Ejemplos:

> “Consulta sobre la propuesta”

> “Capítulo 3”

> “Problema con archivo”
En una conversación existente, el asunto permanece arriba como contexto.

---

### 7. `status`
Inicialmente:

```
open
closed
```
No recomiendo empezar con diez estados.

Después podemos derivar:

> pendiente del autor

> pendiente de Admin
a partir de quién escribió último.

---

### 8. `sender_type`
Aquí hay una decisión importante.

No debemos asumir que Admin será siempre una única persona.

Por eso:

```
sender_type
├── author
└── admin
```
Y:

```
sender_id
```
identificará al usuario correspondiente.

Esto nos deja margen para que posteriormente existan varios usuarios administrativos sin rehacer `messages`.

---

### 9. Lectura
Cada mensaje tendrá:

```
read_at
```
`null`:

> no leído.
Fecha:

> leído.
Esto permite calcular:

- mensajes pendientes;
- contador;
- conversaciones con actividad.

---

### 10. RLS
Aquí no confiaríamos en React.

### Autor
Puede:

- ver sus conversaciones;
- ver mensajes de sus conversaciones;
- crear mensajes en sus conversaciones;
- crear conversaciones;
- marcar sus mensajes como leídos.

### Admin
Puede:

- ver conversaciones gestionables;
- leer mensajes;
- responder;
- crear conversaciones administrativas;
- cerrar conversaciones.
La implementación exacta de “qué Admin puede ver qué” la definiremos antes de tocar Supabase.

---

### 11. No mezclar `notifications`
Cuando llega un mensaje:

```
messages
    ↓
notification
```
Pero son entidades distintas.

La notificación simplemente informa:

> “Tienes un nuevo mensaje.”
Y apunta a la conversación.

---

### 12. No mezclar `reviews`
Una conversación puede tener:

```
project_id
```
y eventualmente referencia contextual a una revisión.

Pero la review sigue siendo la fuente del feedback editorial estructurado.

---

### 13. No mezclar `timeline`
Enviar un mensaje podría generar un evento de timeline:

> “Autor envió un mensaje.”
Pero eso será una decisión de reglas de eventos.

No almacenaremos el contenido del mensaje dentro de `timeline`.

---

### 14. Servicio
Crearemos posteriormente un servicio específico:

```
src/services/message.service.ts
```
o, si al revisar convenciones del repositorio resulta mejor:

```
src/services/conversation.service.ts
```
Su responsabilidad será:

- listar conversaciones;
- crear conversación;
- obtener mensajes;
- enviar mensaje;
- marcar leído;
- cerrar conversación.
No tendrá lógica visual.

---

### 15. Componentes
Eso queda para **1B.3**.

Conceptualmente necesitaremos:

```
ConversationList
ConversationItem
ConversationView
MessageBubble
MessageComposer
SupportConversation
```
Pero **no los implementamos ahora**.

---

### 16. Realtime
No lo convertiría en requisito de la primera versión.

Primero:

```
enviar
↓
persistir
↓
actualizar UI
```
Después podremos añadir Supabase Realtime si queremos:

> “el mensaje aparece instantáneamente sin refrescar”.
La arquitectura propuesta no impide hacerlo.

---

### 17. Adjuntos
Tampoco entran ahora.

Pero `messages` puede evolucionar posteriormente hacia:

```
messages
   ↓
message_attachments
```
sin romper conversaciones.

---

# Decisión técnica
Mi propuesta es:

> **dos tablas nuevas (`conversations` + `messages`), RLS desde el inicio, `project_id` opcional, tipos de conversación, estado simple y mensajes separados de notificaciones/reviews/timeline.**
No modificaría ninguna tabla existente para convertirla artificialmente en chat.

Y antes de crear esas tablas haríamos **1B2.2.4 — Reglas de eventos y comportamiento**, donde definiremos exactamente:

- quién puede iniciar conversación;
- cuándo se crea automáticamente;
- cuándo una notificación acompaña a un mensaje;
- quién recibe qué;
- cómo se marca leído;
- cómo se cierra;
- qué ocurre cuando cambia el proyecto;
- y qué NO debe generar mensajes.
**Después de 1B2.2.4 vendrá 1B2.2.5 — Especificación de implementación.**

Ahí tendremos el contrato completo antes de tocar Supabase.
