Seguimos con 1B2.2.4 — Reglas de eventos y comportamiento de Comunicación.
Y aquí fijamos una regla importante: un mensaje es una acción explícita de comunicación; no vamos a fabricar conversaciones automáticamente por cada evento del sistema.
Reglas principales
1. Autor inicia conversación
Puede crear una conversación general, de proyecto o de soporte.
Si está dentro de una obra, podemos asociarla al project_id.
Se crea la conversación y su primer mensaje en una operación coherente.
2. Admin inicia conversación
Puede iniciar una conversación con un autor.
Puede asociarla a un proyecto.
Esto será útil para propuestas, coordinación editorial o solicitudes concretas.
3. Respuesta
Cada respuesta crea un nuevo registro en messages.
No se crea una conversación nueva.
4. Nuevo mensaje → notificación
Cuando alguien envía un mensaje:
mensaje confirmado
      ↓
notificación al otro participante
La notificación será secundaria al mensaje.
5. No duplicar
Un retry del envío no debe generar dos mensajes ni dos notificaciones.
La deduplicación será parte de la implementación.
6. Leído
Abrir una conversación puede marcar como leído los mensajes destinados al usuario actual.
No se marca como leído simplemente porque aparezca en la lista.
7. Cerrar
Cerrar una conversación no la elimina.
open → closed
El historial permanece.
Si posteriormente alguien responde, podremos decidir si se reabre automáticamente; mi propuesta es sí, porque una conversación con nueva actividad vuelve a estar activa.
8. Soporte
El botón de soporte crea una conversación type = support.
No crea una tabla diferente.
9. Editorial
Una conversación editorial puede apuntar a un proyecto, pero una review sigue siendo una review.
No convertiremos las observaciones estructuradas en mensajes.
10. Propuesta
Una propuesta disponible puede generar una notificación.
No debe crear automáticamente una conversación.
Solo habrá conversación si alguien realmente inicia comunicación.
11. Notificaciones
Mensaje:
messages
   ↓
notification
Pero:
notification
   X
   ↓
message
No crearemos mensajes artificialmente desde notificaciones.
12. Timeline
No todo mensaje tiene que convertirse automáticamente en una entrada de timeline.
Si más adelante queremos registrar:
“Se envió un mensaje”

lo trataremos como evento separado.
13. Internal Notes
Nunca generan mensajes para el autor.
14. Eliminación
La primera versión no tendrá borrado físico de mensajes.
El historial de comunicación debe conservarse.
15. Adjuntos
No generan una arquitectura paralela todavía. Quedan preparados para una futura extensión.
Flujo completo
AUTOR
  │
  ├── escribe mensaje
  │
  ▼
messages
  │
  ├── conversación existente
  │
  └── nueva conversación
          │
          ▼
     notification
          │
          ▼
       ADMIN
Y al revés:
ADMIN
  │
  ▼
messages
  │
  ▼
notification
  │
  ▼
AUTOR
Lo que deliberadamente NO hacemos
No vamos a generar automáticamente:
una conversación cuando cambia una fase;
una conversación cuando aparece una review;
una conversación cuando se crea una propuesta;
una conversación cuando se sube un archivo;
una conversación cuando aparece una notificación.
Esos sistemas pueden notificar.
La conversación aparece cuando existe una necesidad real de conversar.
Con esto queda definido el comportamiento de 1B2.2.4.
