Vamos con 1B2.2.5 — Especificación de implementación. Esta es la última subfase de diseño de Comunicación antes de tocar código o Supabase.
1B2.2.5 — Contrato de implementación
1. Base de datos
Crear solamente:
conversations
messages
Relación:
authors
   │
   └── conversations
          │
          └── messages
          
projects
   │
   └── conversations (opcional)
No modificaremos reviews, notifications, timeline, internal_notes ni proposals para convertirlos en mensajería.
2. conversations
Campos previstos:
id
author_id
project_id       nullable
type
subject
status
created_at
updated_at
Restricciones:
author_id obligatorio.
project_id opcional.
type controlado.
status controlado.
timestamps automáticos.
Tipos iniciales:
general
project
editorial
proposal
support
Estados:
open
closed
3. messages
Campos:
id
conversation_id
sender_type
sender_id
body
created_at
read_at
Restricciones:
conversation_id obligatorio.
sender_type limitado a author / admin.
body no vacío.
read_at nullable.
4. Índices
Desde el inicio:
conversations(author_id)
conversations(project_id)
conversations(status)
conversations(updated_at)

messages(conversation_id)
messages(sender_id)
messages(created_at)
La razón es sencilla: las dos consultas más frecuentes serán:
“Dame mis conversaciones”

y:
“Dame los mensajes de esta conversación ordenados”.

5. RLS
Esto se implementa antes de conectar la UI.
Autor:
SELECT sus conversaciones.
INSERT conversaciones propias.
SELECT mensajes de sus conversaciones.
INSERT mensajes en sus conversaciones.
actualizar lectura de sus mensajes.
Admin:
SELECT conversaciones gestionables.
INSERT conversaciones.
SELECT mensajes.
INSERT mensajes.
cerrar conversaciones.
Y aquí habrá que comprobar exactamente cómo identifica actualmente el proyecto al usuario administrativo antes de escribir las políticas definitivas.
6. Servicio
Crear:
src/services/conversation.service.ts
Responsabilidades:
listConversations()
getConversation()
createConversation()
sendMessage()
markMessagesRead()
closeConversation()
reopenConversation()
Y si la convención existente favorece message.service.ts, podremos usar ese nombre; no crearemos dos servicios redundantes.
7. Notificaciones
Después de confirmar que sendMessage() terminó correctamente:
sendMessage()
     ↓
INSERT messages
     ↓
notification al receptor
La notificación tendrá que enlazar conceptualmente con la conversación.
Pero no alteraremos todavía notifications sin comprobar primero si necesitamos ampliar su modelo.
8. Dashboard
La nueva sección será:
/dashboard/messages
Y Soporte:
/dashboard/support
Pero no necesitamos dos motores.
Ambos utilizan:
Conversation
con diferente type.
9. Admin
Propuesta:
/admin/messages
Con interfaz orientada a gestión:
conversaciones
        ↓
autor
        ↓
proyecto
        ↓
último mensaje
        ↓
estado
No vamos a meter el chat entero dentro de /admin/page.tsx.
Eso perpetuaría precisamente el problema de páginas monolíticas que estamos corrigiendo.
10. Componentes
En 1B.3 podremos crear/reutilizar:
ConversationList
ConversationItem
ConversationView
MessageBubble
MessageComposer
ConversationHeader
Y posiblemente:
ConversationBadge
ConversationFilters
Pero no implementamos estos componentes en 1B2.2.
Aquí solamente queda especificado qué necesitamos.
11. Pruebas mínimas
Antes de considerar Comunicación terminada:
Caso A
Autor crea conversación → Admin la ve.
Caso B
Admin responde → Autor la ve.
Caso C
Autor responde → aparece en la misma conversación.
Caso D
Abrir conversación → mensajes se marcan correctamente como leídos.
Caso E
Cerrar conversación → historial permanece.
Caso F
Nuevo mensaje → una sola notificación.
Caso G
Usuario A intenta acceder a conversación de usuario B → RLS lo bloquea.
Caso H
Conversación asociada a proyecto → solo usuarios autorizados pueden acceder.
Caso I
Conversación general sin proyecto → funciona igualmente.
Caso J
Retry del envío → no duplica mensajes.
