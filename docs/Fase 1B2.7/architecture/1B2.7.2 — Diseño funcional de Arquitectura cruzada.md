# Diseño funcional de Arquitectura cruzada Dashboard/Admin — 1B2.7.2

Este documento define la estrategia para armonizar la lógica de negocio entre Dashboard (Autor) y Admin, centralizando el dominio y separando las responsabilidades de interfaz.

## 1. Principio fundamental
Ambos entornos deben consumir las mismas reglas de dominio y modelos de datos. La diferencia entre Admin y Dashboard no reside en la lógica de negocio, sino en la **experiencia de usuario** (gestión operativa vs. narrativa narrativa/visual).

## 2. Capa de Dominio Compartida
Se establecerá un núcleo de conocimiento común:
- **Modelos de Dominio**: Definiciones unificadas (`Project`, `Proposal`, `Feedback`, etc.) en lugar de interpretaciones aisladas en cada servicio.
- **Fuentes de Verdad**: La lógica que define los estados y fases del proyecto se centraliza, eliminando la duplicación entre el "journey" del Dashboard y el mapping de Admin.
- **`EditorialJourney`**: Se implementará una función única (`deriveEditorialJourney`) que calcula las seis fases editoriales a partir de los estados reales (`projects.status`, `reviews`, etc.), garantizando coherencia en ambos lados.

## 3. Separación de Responsabilidades
- **Dominio**: Reglas sobre qué es un proyecto, cómo se acepta una propuesta o cómo se marca un feedback como resuelto.
- **UI (Dashboard/Admin)**:
    - **Dashboard**: Enfoque narrativo, centrado en el progreso del autor.
    - **Admin**: Enfoque operativo, centrado en la gestión y orquestación.

## 4. Servicios y Orquestación
- **Servicios Específicos**: Se mantendrán servicios atómicos (`proposal.service.ts`, `review.service.ts`, etc.) como autoridad sobre las entidades.
- **Orquestación**: `admin.service.ts` evolucionará a un orquestador de alto nivel, dejando de duplicar la lógica de negocio que reside en los servicios específicos.
- **No duplicidad**: No se recreará lógica de negocio dentro de los componentes visuales o hooks de la interfaz.

## 5. ViewModels para asimetría visual
Se utilizarán **ViewModels** para adaptar el modelo de dominio a las necesidades de cada rol:
- `AdminProjectViewModel` (datos densos para gestión).
- `AuthorProjectViewModel` (datos narrativos para el autor).
Ambos consumen el mismo modelo de dominio central, evitando recrear la misma lógica en cada vista.

## 6. Sincronización y Seguridad
- **RLS**: Se mantiene como única barrera de seguridad, aplicándose transversalmente sin importar la UI.
- **Autoridad de Operación**: Las acciones que cambian el estado de negocio (ej: `acceptProposal`) residen en el backend (servicios), siendo independientes de la interfaz que las invoque.

### Resultado de 1B2.7.2
**La arquitectura cruzada se formaliza centrada en un modelo de dominio único.**
- Admin y Dashboard comparten la lógica de negocio.
- Se eliminan interpretaciones divergentes de estados y fases.
- La UI (Dashboard/Admin) es una proyección de este dominio, adaptada según las necesidades de cada usuario, pero sin poseer la autoridad del flujo.

*El siguiente paso será **1B2.7.3 — Modelo técnico de la arquitectura cruzada**, donde aterrizaremos esta estructura a carpetas, tipos de datos y la reorganización de los servicios actuales.*


Vamos con 1B2.7.2 — Diseño funcional de la arquitectura cruzada Dashboard/Admin.
Aquí ya no estamos auditando qué hay: vamos a definir cómo deben convivir ambos lados sin duplicar lógica, manteniendo diseños distintos donde tenga sentido.
1B2.7.2 — Diseño funcional
1. Principio central
La arquitectura será:
                 MODELO DE DOMINIO
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
        Dashboard                Admin
       experiencia              gestión
No:
Dashboard → su propia lógica
Admin     → otra lógica
Ambos consumen las mismas reglas del dominio.
2. Qué significa “compartir”
No significa que Admin y Dashboard tengan la misma UI.
Significa que ambos deben reconocer exactamente igual:
qué es un proyecto;
qué significa cada estado;
qué es una propuesta;
qué es feedback;
qué es actividad;
qué es una notificación;
qué pertenece al autor;
qué pertenece exclusivamente a Admin.
3. Capa de dominio compartida
La nueva arquitectura lógica debe concentrar conceptos como:
Project
ProjectStatus
ProjectPhase
RequestStatus
ProposalStatus
ReviewStatus
TimelineEvent
Notification
Y reglas de transformación:
DB → dominio
dominio → UI
Eso evita que admin.service.ts y project.service.ts traduzcan la misma cosa de dos formas.
4. projects.status
La fuente maestra será:
projects.status
con:
planning
production
review
completed
archived
Admin dejará de tener un mapping conceptual independiente.
Dashboard tampoco tendrá otro catálogo de estados.
Ambos consumirán una definición compartida:
planning
→ Análisis

production
→ Producción

review
→ Revisión

completed
→ Completado
archived será tratado como un estado técnico/administrativo, no como una nueva fase editorial.
5. Las seis fases del autor
Esto es importantísimo por todo lo que detectamos antes.
Las seis fases:
Recibido
Análisis
Propuesta
Producción
Revisión
Completado
no deben convertirse directamente en seis valores de projects.status.
En cambio, serán una experiencia derivada del estado global y de otros hitos reales.
Por ejemplo:
project_request.status
        +
evaluation
        +
proposal
        +
projects.status
        +
reviews
producen:
EditorialJourney
Así podemos mostrar seis fases sin inventar seis estados físicos dentro de projects.
6. Una única EditorialJourney
Debe existir una única función/modelo conceptual:
deriveEditorialJourney(...)
que reciba las fuentes reales y devuelva:
[
  Recibido,
  Análisis,
  Propuesta,
  Producción,
  Revisión,
  Completado
]
Tanto Dashboard como Admin pueden utilizarlo.
Pero:
Dashboard
lo presenta narrativamente.
Admin
lo presenta operativamente.
7. Ejemplo
Supongamos:
project_request.status = evaluating
y:
evaluations.result = approved
pero:
proposal.status = pending
La ruta puede quedar:
✅ Recibido
✅ Análisis
🟡 Propuesta
○ Producción
○ Revisión
○ Completado
No necesitamos cambiar projects.status para representar esto.
8. Propuesta aceptada
Si:
proposal.status = accepted
y:
projects.status = production
entonces:
✅ Recibido
✅ Análisis
✅ Propuesta
🟡 Producción
○ Revisión
○ Completado
Esto resuelve definitivamente el problema que discutimos al principio:
Tres/cuatro estados internos no tienen que transformarse matemáticamente en seis.

Las seis fases son una capa de producto derivada de varias fuentes reales.
9. Timeline
Timeline no calcula la ruta.
La relación correcta:
EditorialJourney
= estado derivado actual

Timeline
= historial de acontecimientos
Ejemplo:
Ruta actual: Producción

Actividad:
• Propuesta aceptada
• Proyecto activado
• Capítulo 1 creado
No invertimos esa dependencia.
10. Admin no modifica la ruta directamente
Admin modifica entidades reales:
project_request
evaluation
proposal
project
review
deliverable
Después la ruta editorial se deriva.
Esto elimina acciones del tipo:
“Cambiar fase del autor”

que podrían modificar una capa puramente visual.
11. ¿Qué servicio debe tocar qué?
La regla funcional:
request.service
solicitudes.
evaluation.service
evaluaciones.
proposal.service
propuestas.
project.service
proyectos.
review.service
feedback.
timeline.service
actividad.
notification.service
avisos.
communication.service
mensajes.
internal-notes.service
notas privadas.
Admin puede orquestarlos, pero no reemplazarlos.
12. Papel de admin.service
admin.service deja de ser una “segunda lógica de dominio”.
Su papel será:
orquestador de operaciones administrativas.

Ejemplo:
Admin
  ↓
adminService.acceptProposal()
  ↓
proposalService.acceptProposal()
No:
adminService
  ↓
UPDATE proposals
  ↓
CREATE project
  ↓
INSERT notification
todo mezclado en el mismo archivo.
13. Papel de Dashboard
Dashboard será consumidor del dominio.
Ejemplo:
Dashboard
  ↓
getAuthorWorkspace()
  ↓
domain models
  ↓
UI
No debe saber:
cómo funciona RLS;
cómo hacer joins complejos;
cómo se crea una propuesta;
cómo se actualiza una review.
14. Papel de Supabase
Supabase es la persistencia y seguridad.
Pero hay que evitar que:
frontend
+
RPC
+
trigger
todos implementen el mismo flujo de negocio.
Eso es exactamente lo que detectamos con las funciones de sincronización.
15. Funciones de Supabase
Las funciones tipo:
sync_project_request_from_manuscript()
sync_projects_from_accepted_request()
no deben competir con la lógica de dominio de frontend.
La regla de diseño será:
una operación de negocio debe tener una autoridad clara.

Si una operación se vuelve transaccional y crítica para integridad, la DB puede ser esa autoridad.
Si no, el servicio de dominio puede coordinarla.
Pero nunca ambos hacen lo mismo silenciosamente.
16. Autoridad para aceptar propuesta
El diseño recomendado:
acceptProposal()
será una operación de dominio única.
No:
Dashboard → UPDATE proposal
Admin     → UPDATE proposal
RPC       → UPDATE project
trigger   → UPDATE proposal
Todos terminan en la misma regla.
17. Autoridad para cambio de proyecto
Admin puede cambiar el estado del proyecto.
Dashboard no.
Pero ambos leen:
projects.status
y el mismo ProjectStatus.
Esto es un ejemplo de:
misma fuente
≠
mismos permisos
18. Autoridad para Feedback
Admin crea/resuelve feedback.
Autor:
lo lee;
responde mediante el mecanismo definido;
no altera arbitrariamente el estado editorial interno.
Ambos consumen:
reviews
19. Autoridad para Notificaciones
El servicio de Notifications es compartido.
Pero:
Admin
→ puede generar

Autor
→ puede leer y marcar como leído
No es necesario duplicar componentes de persistencia.
20. Autoridad para Timeline
Timeline es de solo lectura para el producto en general.
La escritura debe venir de operaciones de dominio.
No desde:
Dashboard useEffect
Admin render
21. Internal Notes
Queda fuera del dominio compartido visible al autor.
Pero sí comparte:
ProjectContext
con Admin.
Así:
AdminProjectWorkspace
├── Feedback
├── Timeline
├── Internal Notes
└── ...
todos reciben el mismo projectId.
22. Selección de obra
Esta es una de las cosas que más queremos evitar duplicar.
Dashboard
Tiene su obra seleccionada.
Admin
Tiene su obra seleccionada.
Pero no necesitan compartir un estado React global.
Lo que comparten es el contrato:
SelectedProject
y su identidad:
projectId
Cada experiencia puede manejar su navegación/selección de forma independiente.
23. Qué no hacer
No crear:
GlobalDashboardAdminStore
solo para compartir el ID.
Sería demasiada infraestructura.
La arquitectura debe compartir dominio, no necesariamente estado de UI.
24. ViewModels
Una fuente frecuente de duplicación actual es:
AdminProject
AuthorProjectData
que representan parcialmente el mismo objeto.
La solución no es necesariamente eliminar ambos.
La solución es:
ProjectDomainModel
y luego:
AdminProjectViewModel
AuthorProjectViewModel
Así cada interfaz conserva sus necesidades visuales sin inventar datos diferentes.

Dominio:
Project {
  id
  authorId
  manuscriptId
  status
  proposalId

AdminProjectViewModel {

27. Navegación
No debemos hacer que Dashboard y Admin compartan rutas.
Ejemplo:
/dashboard/propuesta
/admin/propuesta
pueden apuntar al mismo dominio:

pero tener experiencias completamente diferentes.
28. Errores
La capa de dominio normaliza errores de Supabase.
La UI decide cómo mostrarlos.
Así no tenemos:
Dashboard
→ error wording A

Admin
→ error wording B
para la misma operación.
29. Seguridad
La capa compartida nunca debe saltarse RLS.
La arquitectura correcta es:
UI
 ↓
domain service
 ↓
Supabase client
 ↓
RLS
No:
UI
 ↓
service_role
30. Objetivo de la 1B.7
Después de implementar esta arquitectura queremos poder decir:
Si cambia la semántica de una propuesta, se modifica una sola capa.

Y entonces:
Admin se actualiza;
Dashboard se actualiza;
Timeline se actualiza;
Notifications se actualizan;
sin reescribir cuatro implementaciones.

32. Decisión funcional de 1B2.7.2
Queda establecido:
Dashboard y Admin compartirán una misma capa conceptual de dominio, modelos y reglas, pero mantendrán ViewModels, navegación y diseños propios.

Y además:
Ninguna UI podrá convertirse en fuente de verdad del estado editorial.

La fuente seguirá siendo:
Supabase business entities
        ↓
Domain
        ↓
Dashboard / Admin
Con esto solucionamos la raíz del problema que encontramos en la auditoría: mismo backend, reglas diferentes.
