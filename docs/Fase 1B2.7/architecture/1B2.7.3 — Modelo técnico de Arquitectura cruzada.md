# Modelo técnico de Arquitectura cruzada Dashboard/Admin — 1B2.7.3

Este documento define la estructura técnica que permitirá armonizar Dashboard (Autor) y Admin, centralizando la lógica de negocio en una capa de dominio compartida y delegando la representación visual a ViewModels específicos para cada rol.

## 1. Arquitectura Objetivo
La estructura sigue un modelo de capas donde la lógica de negocio es agnóstica a la interfaz:
`UI` -> `Hooks` -> `Servicios de Dominio` -> `Supabase (Persistencia/RLS)`.

## 2. Organización de la Capa de Dominio
- **`domain/`**: Definición de modelos de negocio (interfaces) independientes del esquema de base de datos (`Database['public']['Tables']`).
- **`services/`**: Servicios atómicos centrados en capacidades (`project.service.ts`, `proposal.service.ts`, etc.). Cada servicio es responsable de una única entidad o flujo.
- **Transformación**: La lógica de cálculo editorial (`EditorialJourney`) y mapeo de estados se centraliza en funciones de dominio puras, accesibles por ambos entornos.

## 3. ViewModels (Asimetría Visual)
Para evitar la duplicación de datos sin forzar diseños idénticos:
- **`AdminProjectViewModel`**: Contiene la visión operativa completa (notas internas, métricas, gestión).
- **`AuthorProjectViewModel`**: Contiene la visión narrativa y colaborativa del autor.
- Ambos se derivan de modelos de dominio comunes, asegurando que los datos compartidos (estados, fases) tengan la misma interpretación.

## 4. Orquestación y Servicios
- **`admin.service.ts`**: Evolucionará de ser un "contenedor de todo" a un orquestador que invoca los servicios de dominio específicos.
- **Servicios por capacidad**: Cada servicio (`review.service`, `proposal.service`) encapsula las reglas de negocio, validaciones y acceso a Supabase, evitando lógica en los componentes de UI.

## 5. Gestión del Estado
- **Estado de UI**: Cada entorno (Admin/Dashboard) gestiona su estado local de forma independiente.
- **Identidad de Proyecto**: Se utiliza un `projectId` explícito compartido por contexto, evitando un `Store` global innecesario.
- **Deduplicación**: Las operaciones de escritura garantizan la idempotencia desde el servicio de dominio, sin depender de la UI.

## 6. Integración y Seguridad
- **RLS**: Se mantiene como única barrera. La capa de servicio no reemplaza la seguridad de Supabase.
- **Atomicidad**: Operaciones complejas (ej: aceptar propuesta + activar proyecto) se realizan mediante llamadas atómicas o transaccionales en el backend/servicio para evitar estados intermedios inconsistentes.

## 7. Estrategia de Implementación
- **Incremental**: No se realizará una reescritura total. Se migrará lógica desde los servicios actuales hacia los servicios de dominio conforme se toquen los módulos.
- **Normalización de Errores**: Centralización de la interpretación de errores para que Admin y Dashboard compartan mensajes coherentes.

3. database.types.ts
Sigue siendo la representación del esquema real de Supabase.
No debe convertirse en un modelo de UI.
Por ejemplo:
Database['public']['Tables']['projects']['Row']
describe la fila de Supabase.
No describe:
“cómo se ve un proyecto en Dashboard”.

4. domain.types.ts
Necesitamos separar el modelo de negocio del esquema de persistencia.
Ejemplo:
export type ProjectStatus =
  | 'planning'
  | 'production'
  | 'review'
  | 'completed'
  | 'archived';

export interface Project {
  id: string;
  authorId: string;
  manuscriptId: string;
  proposalId: string | null;
  status: ProjectStatus;
}
Esto permite que Admin y Dashboard compartan el mismo concepto.
5. EditorialJourney
Debe existir como modelo de dominio, no como estado local de Dashboard.
Algo conceptualmente parecido a:
export type EditorialPhase =
  | 'received'
  | 'analysis'
  | 'proposal'
  | 'production'
  | 'review'
  | 'completed';
Y:
interface EditorialJourney {
  currentPhase: EditorialPhase;
  phases: EditorialPhaseState[];
}
Esto se deriva de:
project_requests
evaluations
proposals
projects
reviews
No se almacena como una sexta tabla.
6. deriveEditorialJourney

deriveEditorialJourney(context): EditorialJourney

seis fases del producto
Así desaparecen:

como dos interpretaciones diferentes.

33. Decisión técnica final
La arquitectura de 1B2.7.3 queda definida así:
Una sola capa de dominio compartida, ViewModels específicos para Dashboard y Admin, servicios especializados por capacidad, y Supabase como persistencia + seguridad.

No crearemos un “super servicio” global.
No compartiremos estado React innecesariamente.
No haremos que Admin y Dashboard dependan entre sí.
Y, sobre todo, no habrá dos interpretaciones distintas de un mismo estado de negocio.
Con esto queda preparado 1B2.7.4 — Reglas de comportamiento de la arquitectura cruzada, donde vamos a fijar qué puede leer/modificar cada lado, cómo se sincronizan cambios, qué pasa ante conflictos y qué camino tiene prioridad cuando existen servicios y funciones de Supabase que actualmente hacen lo mismo.
