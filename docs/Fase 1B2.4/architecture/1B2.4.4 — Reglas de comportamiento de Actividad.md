# Reglas de comportamiento de Actividad / Timeline — 1B2.4.4

Este documento establece las reglas de negocio para el módulo de Timeline, asegurando que la actividad registrada sea veraz, persistente y diferenciada de otros sistemas (notificaciones, logs técnicos, etc.).

## 1. Principio de veracidad
El Timeline solo registra **acontecimientos de negocio reales y confirmados**. No se registran intenciones, estados temporales de la interfaz ni eventos puramente técnicos (refrescos, errores de red).

## 2. Catálogo de eventos relevantes
- **Proyecto**: `project_created`, `project_stage_changed`, `project_completed`.
- **Manuscrito**: `manuscript_received`, `manuscript_evaluation_completed`.
- **Producción**: `chapter_created`, `chapter_delivered`, `deliverable_created`, `deliverable_approved`.
- **Feedback**: `review_created`, `review_resolved`, `review_discarded`.
- **Propuestas**: (A definir en implementación).
- **Comunicación**: Eventos críticos relevantes (ej: cierre de conversación).

## 3. Comportamiento ante cambios de estado
- **Atomicidad**: El evento debe registrarse en el mismo proceso de negocio que la acción real. Si la acción falla, no hay registro en Timeline.
- **Deduplicación**: Las acciones idempotentes o reintentos no deben generar entradas duplicadas.
- **Inmutabilidad**: El historial es `append-oriented`. No se reescribe el pasado. Las correcciones se gestionan mediante eventos correctivos si fuera necesario.

## 4. Separación de conceptos
- **Estado vs Historial**: `projects.status` y `production_stages` definen el progreso actual. `timeline` registra el historial de hitos. Nunca se usa `timeline` para reconstruir la fase actual.
- **Comunicación**: Los eventos de actividad son independientes de los mensajes. Un mensaje enviado no genera automáticamente una entrada en el Timeline a menos que sea un hito (ej: cierre de conversación).
- **Notificaciones**: La notificación es un aviso (*push*); el Timeline es una fuente de registro (*pull*). La secuencia es: `Evento real` -> (`Timeline` + `Notification`).

## 5. Gestión y Visibilidad
- **RLS**: Se mantiene la política basada en `projects.author_id` para autores y acceso administrativo total.
- **Formato**: 
    - `event`: Clave constante para lógica.
    - `details`: Contexto legible breve.
    - `created_at`: Timestamp UTC.
- **Estado vacío**: Ante la ausencia de actividad, la UI mostrará un estado vacío explícito ("Todavía no hay actividad registrada"), sin generar datos de ejemplo.

## 6. Auditoría técnica vs. Producto
El Timeline es un **historial de producto**. No debe confundirse con logs de auditoría técnica (`audit_logs`) o logs de llamadas API.

---

### Decisión final
La regla fundamental es: **`timeline` registra hitos reales, relevantes, persistentes e inmutables.** 

La separación de responsabilidades queda blindada:
- **`reviews` / `projects` / etc.** = Fuente de verdad actual.
- **`timeline`** = Proyección histórica.
- **`notifications`** = Canales de aviso.
- **`audit_logs`** = Auditoría técnica.

Vamos con 1B2.4.4 — Reglas de comportamiento de Actividad / Timeline.
Aquí cerramos el comportamiento antes de redactar la especificación de implementación.
1. Regla principal
Una entrada de Timeline solo aparece cuando ocurre un acontecimiento de negocio real y confirmado.
acción válida
   ↓
persistencia correcta
   ↓
evento de Timeline
No registramos intenciones ni estados temporales de UI.
2. Proyecto creado
Cuando projects se crea correctamente:
project_created
se registra una sola vez.
Si la creación falla, no hay Timeline.
3. Cambio de fase
Cuando projects.status cambia realmente:
planning → production
se registra:
project_stage_changed
con contexto:
Análisis → Producción

No generamos evento si se guarda el mismo estado que ya existía.
4. Completado
Cuando:
review → completed
se registra:
project_completed
No se vuelve a generar si alguien vuelve a guardar completed.
5. Capítulos
Crear capítulo:
chapter_created
Entregar capítulo:
chapter_delivered
No registramos cada cambio intermedio si no representa un hito visible para el autor.
6. Entregables
Al crear un entregable:
deliverable_created
Al aprobarlo:
deliverable_approved
No registramos:
cada subida temporal;
cada cambio de URL;
cada render;
cada refresh.
7. Feedback
Al crear una review:
review_created
Al resolverla:
review_resolved
Al descartarla:
review_discarded
No generamos:
review_open
cada vez que se consulta.
8. Propuestas
1B2.4 no decidirá todavía el catálogo definitivo de eventos de propuestas.
La regla es:
Solo se registran los eventos que 1B2.5 defina como relevantes.

Así no duplicamos decisiones entre fases.
9. Comunicación
Misma regla.
No convertimos cada mensaje en actividad por defecto.
La decisión sobre:
message_sent
conversation_closed
se coordina con el modelo de Comunicación de 1B2.2.
10. Notificaciones
Una notificación nunca crea un evento de Timeline.
La secuencia correcta es:
evento real
   ├──→ timeline
   └──→ notification
Nunca:
notification
   ↓
timeline
11. Duplicados
Una acción idempotente no debe generar duplicados.
Ejemplo:
Admin pulsa "Cambiar a Producción"
Si el estado ya es production, no debe aparecer otra entrada project_stage_changed.
Para eventos donde la acción pueda reintentarse, la implementación debe definir una estrategia de deduplicación antes de construirlos.
12. Fallo parcial
La regla será:
No publicar una actividad que represente una acción que finalmente falló.

Ejemplo:
UPDATE projects
   ↓
falla
   ↓
NO timeline
Y preferiblemente:
UPDATE projects
   +
INSERT timeline
deben tratarse de forma coherente para no dejar al usuario viendo un historial falso.
La forma exacta de garantizar esa atomicidad queda para 1B2.4.5.
13. Orden temporal
Timeline se mostrará por:
created_at DESC
La entrada más reciente arriba.
No usaremos índices visuales manuales para ordenar acontecimientos históricos.
14. Fecha y hora
La persistencia usará UTC/timestamp con zona horaria.
La UI transforma la fecha según el contexto/localización.
No guardaremos textos como:
“Hace 2 horas”

en la base.
15. Edición
Una entrada histórica no debería editarse para “reescribir el pasado”.
Por defecto:
Timeline es append-oriented.
Si hubo un error de aplicación, la corrección debe resolverse mediante:
un evento correctivo, o
una operación administrativa controlada.
No mediante edición silenciosa del historial.
16. Eliminación
El usuario normal no elimina actividad.
Admin tampoco debería borrar eventos como parte de la operación cotidiana.
La política actual tiene timeline_admin_delete; habrá que decidir en la implementación si esa capacidad se mantiene para mantenimiento controlado o se retira del flujo normal. 
17. Visibilidad
Autor:
solo actividad de sus proyectos.

Admin:
actividad de los proyectos que administra.

La política RLS actual ya parte de esa relación con projects. 
18. Cambio de proyecto
Una entrada siempre queda ligada al project_id original.
No se mueve automáticamente si el proyecto cambia de manuscrito o si se reorganiza la información.
El historial debe conservar su contexto original.
19. Actividad y Ruta editorial
No hay que reconstruir las seis fases desde Timeline.
Ejemplo:
Ruta actual:
Revisión

Actividad:
Proyecto pasó a Producción
Entregable creado
Feedback creado
Feedback resuelto
La Ruta sigue siendo el estado actual.
Timeline sigue siendo el historial.
20. Actividad y Timeline visual actual
La interfaz puede mostrar un subconjunto de los eventos persistidos.
Eso significa:
Supabase timeline
        ↓
selector/filtro
        ↓
Dashboard
El Dashboard no inventa eventos para completar huecos visuales.
21. Vacío
Actualmente timeline tiene 0 filas.
Por tanto, la UI necesita un estado vacío legítimo:
“Todavía no hay actividad registrada para esta obra.”

No se deben fabricar entradas de ejemplo.
22. Auditoría / debugging
La actividad visible al usuario no sustituye audit_logs.
Queda:
timeline
= historial de producto

audit_logs
= auditoría técnica/administrativa
No mezclarlos.
Decisión cerrada de 1B2.4.4
La regla general queda:
Timeline registra hitos reales, relevantes, persistentes e inmutables por defecto. Las tablas de negocio son las fuentes maestras; Timeline es su historial visible. Notificaciones son canales de aviso, y Audit Logs son auditoría técnica.

Y quedan especialmente protegidos cuatro límites:
Ruta ≠ Timeline
Timeline ≠ Notificaciones
Timeline ≠ Mensajes
Timeline ≠ Audit Logs
Con esto ya tenemos 1B2.4.1 → .4.
