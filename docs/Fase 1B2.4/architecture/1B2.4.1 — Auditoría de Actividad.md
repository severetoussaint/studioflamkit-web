# Auditoría de 1B2.4 — Actividad / Timeline

Esta auditoría mapea el estado actual del sistema de Timeline, identificando la discrepancia entre la existencia de la tabla en Supabase y la falta de alimentación automática de eventos.

## 1. Qué existe realmente
Supabase contiene la tabla `public.timeline`, que incluye `id`, `project_id`, `event`, `details` y `created_at`.
- **Estado de datos**: A pesar de existir una estructura completa, no hay filas persistidas. La base está preparada, pero el flujo de escritura está cerrado.

## 2. RLS y Seguridad
- **Autor**: Tiene acceso de lectura al Timeline de sus proyectos a través de `projects.author_id`.
- **Admin**: Tiene permisos completos de lectura/escritura.
- **Conclusión**: El modelo de seguridad sí está pensado para actividad por proyecto.

## 3. Alimentación del sistema (Triggers/Funciones)
Actualmente, **Timeline NO se alimenta automáticamente**.
- No existen triggers ni funciones de base de datos que registren automáticamente los cambios en las tablas relacionadas (projects, reviews, etc.).

## 4. UI Dashboard vs. Persistencia
- **Dashboard**: Existe una experiencia visual de "Timeline/recorrido editorial".
- **Discrepancia**: Esta UI no parece estar leyendo de `public.timeline`, dado que la tabla está vacía. Se infiere que la UI utiliza datos derivados o estados en tiempo real, no un historial persistente.

## 5. Panel Admin
No existe una sección dedicada de "Actividad" o "Timeline" para el Admin. Los cambios se gestionan a través de acciones operativas, pero no hay trazabilidad histórica gobernada desde este panel.

## 7. Conclusión operativa
El riesgo principal es implementar una capa visual que "simule" eventos. La premisa del proyecto es **información real, nunca simulada**. 

Timeline debe representar un **historial de acontecimientos relevantes y confirmados**, no un log técnico ni una copia de estados maestros. La tarea crítica es definir el puente entre `acontecimiento real` -> `persistencia` -> `timeline` -> `presentación`.

9. Qué NO debe convertirse en Timeline
No debemos registrar:

cada refresh;

cada lectura de un archivo;

Timeline debe representar acontecimientos relevantes del proyecto.
10. Qué debería representar Timeline
La definición que recomiendo para 1B2.4 es:
Timeline = historial de acontecimientos relevantes y confirmados de una obra/proyecto.

No es:
estado maestro;
chat;
notificación;
review;
log técnico.
Es una proyección histórica del proyecto.
