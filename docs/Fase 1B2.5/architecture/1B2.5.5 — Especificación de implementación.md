# Especificación de implementación — 1B2.5.5

Este documento define el contrato técnico final para la integración del flujo de propuestas, estandarizando el proceso desde la solicitud hasta la creación del proyecto.

## 1. Integridad de Esquema
- **Reutilización**: Se mantiene el uso de las tablas `project_requests`, `evaluations`, `proposals` y `projects`.
- **Prohibición**: Queda prohibida la creación de tablas nuevas (`quotes`, `contracts`, etc.) para evitar la duplicidad de fuentes de verdad.

## 2. Servicio de Propuestas (`proposal.service.ts`)
- **API del Servicio**:
    - `listProposals(requestId?)`
    - `getProposal(proposalId)`
    - `createProposal(input)`
    - `sendProposal(proposalId)`
    - `acceptProposal(proposalId)`
    - `rejectProposal(proposalId)`
    - `expireProposal(proposalId)`
- **Lógica de negocio**: Reutilización de los cálculos existentes de cotización. La persistencia se migra de la lógica actual a la tabla `proposals`.

## 3. Modelo de flujo
`Solicitud` (project_requests) → `Evaluación` (evaluations) → `Propuesta` (proposals) → `Decisión` (Aceptar/Rechazar) → `Proyecto` (projects).

## 4. Admin — Interfaz
- **Gestión**: Integración dentro de la sección de solicitudes.
- **Formulario**: Creación formal vinculada a una solicitud existente. Distinción clara entre `Guardar` (borrador) y `Enviar` (formalización).
- **Control**: Impedir edición destructiva sobre propuestas aceptadas.

## 5. Dashboard (Autor) — Interfaz
- **Notificación y Alerta**: Aviso visual claro de propuesta pendiente en el Dashboard.
- **Vista de Detalle**: Interfaz de oferta (Servicios, Monto, Plazos, Expiración) con botones `[Rechazar]` y `[Aceptar propuesta]`.
- **Confirmación**: Se requiere paso de confirmación ("¿Está seguro?") antes de la aceptación definitiva.

## 6. Lógica de Aceptación (Atómica)
Al aceptar (`acceptProposal`):
1. Validación de estado (`pending`) y expiración (`expires_at`).
2. Transición de estado (`pending` -> `accepted`).
3. Creación o activación del `project` si no existe.
4. Vinculación `projects.proposal_id`.
5. Registro en `timeline` y envío de `notification`.
6. Garantía de idempotencia: protección contra dobles activaciones.

## 7. Reglas de Validación
- No permitir propuestas con datos inválidos (montos negativos, servicios vacíos).
- La aceptación solo ocurre si la propuesta está vigente y en estado `pending`.
- Inmutabilidad: una vez aceptada/rechazada, no se edita.

## 8. Integración con Módulos existentes
- **Notificaciones**: Integración con el sistema 1B2.1 para creación, aceptación y rechazo.
- **Timeline**: Registro de hitos (creación, aceptación, rechazo, expiración) según las reglas de 1B2.4.
- **Comunicación**: El botón "Responder" redirige al motor de mensajes (1B2.2), sin insertar contenido dentro de `proposals`.
- **Seguridad (RLS)**: Validación estricta en backend para cada operación de aceptación/rechazo, asegurando que el autor solo actúe sobre sus propias solicitudes.

## 9. Orden de Implementación
1. Implementación de `proposal.service.ts`.
2. Desarrollo de componentes UI (`ProposalCard`, `ProposalDetail`).
3. Integración en Admin (creación/edición).
4. Integración en Dashboard (vista/decisión).
5. Flujo de aceptación/creación de proyecto.
6. Pruebas de integración, RLS y flujo de estados (incluyendo casos de error y reintentos).

   ↓
Evaluación
   ↓
Propuesta
   ↓
Decisión del autor
   ↓
Proyecto

createProposal(input)

acceptProposal(proposalId)

13. Flujo de aceptación
La implementación deberá garantizar:
validar propuesta
       ↓
verificar pending
       ↓
verificar expiración
       ↓
marcar accepted
       ↓
crear/activar proyecto
       ↓
vincular projects.proposal_id
       ↓
registrar Timeline
       ↓
crear Notification
En caso de error crítico, no dejar una aceptación parcialmente completada sin una estrategia explícita de recuperación.
14. Flujo de rechazo
validar pending
       ↓
rejected
       ↓
Timeline
       ↓
Notification Admin
No crear proyecto.
La razón del rechazo puede permanecer en Comunicación en esta primera versión.
15. Flujo de expiración
Al intentar aceptar:
expiresAt < now
entonces:
pending → expired
y la aceptación se rechaza.
La expiración automática periódica queda fuera de esta primera implementación.
16. Vinculación del proyecto
Cuando se crea el proyecto desde una propuesta:
projects.proposal_id = proposal.id
y se conserva:
projects.manuscript_id
projects.author_id
No duplicar:
amount
services
deadline
en projects.
17. Prevención de duplicados
Antes de crear proyecto:
proposalId → existing project?
y también revisar la posibilidad de proyecto existente para el mismo manuscrito.
El caso ambiguo debe detenerse y manejarse explícitamente.
No crear dos proyectos.
18. RLS
Antes de implementación final hay que verificar:
Autor
SELECT solo sobre sus propuestas.
UPDATE solo para aceptar/rechazar la propuesta que le pertenece.
Admin
SELECT, INSERT, UPDATE.
La UI no será la barrera de autorización.

proposal_rejected

Decisión final
La aplicación debe dejar de tratar la cotización como un cálculo aislado dentro de Admin y pasar a un flujo real:
Solicitud → Evaluación → Propuesta → Decisión → Proyecto.
La entidad proposals existente será la fuente de verdad de la oferta formal y projects.proposal_id conservará su procedencia. No se crea una segunda tabla ni se duplica el importe/servicios en projects.
Con esto, 1B2.5 queda cerrada.
