# Diseño funcional de Propuestas — 1B2.5.2

Este documento establece el diseño funcional para integrar formalmente el flujo de propuestas (`proposals`) en la operativa de negocio, conectando la evaluación del Admin con la decisión del Autor.

## 1. Cadena de valor formalizada
El flujo funcional se estandariza como:
`Solicitud` (project_requests) → `Evaluación` (evaluations) → `Propuesta` (proposals) → `Decisión` (aceptar/rechazar) → `Proyecto` (projects).

## 2. Definición de Etapas
- **Solicitud**: Petición inicial del autor.
- **Evaluación**: Análisis interno (Admin) sobre viabilidad y condiciones.
- **Propuesta**: Oferta formal presentada al autor (fuente de verdad: `proposals`).
- **Decisión**: Acción del autor (Aceptar/Rechazar) que determina el ciclo de vida del proyecto.

## 3. Experiencia de Admin
- **Gestión centralizada**: La interfaz de Admin pasa de "Cotización" (calculada en memoria) a "Propuesta" (gestionada sobre `proposals`).
- **Workflow**:
    - Generar propuesta a partir de evaluación.
    - Acciones diferenciadas: `Guardar` (borrador) vs `Enviar` (formalización).
- **Listado**: Vista operativa de solicitudes/propuestas por estado.

## 4. Experiencia del Autor (Dashboard)
- **Notificación y visibilidad**: El autor recibirá notificaciones ante propuestas pendientes.
- **Sección dedicada**: "Propuestas" dentro de la obra/proyecto.
- **Vista de detalle**: Interfaz clara de oferta (Servicios, Monto, Plazos, Expiración) con botones de acción `[Rechazar]` y `[Aceptar propuesta]`.
- **Confirmación**: Se implementará un paso de confirmación ("¿Está seguro?") antes de la aceptación definitiva para evitar errores.

## 5. Estados de la Propuesta
Coincidiendo con la base de datos: `pending`, `accepted`, `rejected`, `expired`.
- El flujo visual seguirá estos estados, evitando inventar estados persistentes adicionales innecesarios.

## 6. Gestión de Resultados
- **Aceptación**: Si se cumplen los requisitos administrativos, la aceptación formaliza el proyecto, enlazando `projects.proposal_id`.
- **Rechazo**: Opcional solicitud de motivo para retroalimentación interna.

## 7. Relación con módulos existentes
- **Comunicación**: El módulo de Mensajes (1B2.2) queda disponible como soporte para dudas sobre la propuesta, manteniendo la propuesta como objeto editorial estructurado.
- **Notificaciones**: Avisos sobre creación/actualización de propuestas.
- **Timeline**: Registro de hitos (creación, aceptación, rechazo).
- **Evaluaciones**: La propuesta se nutre de la evaluación técnica realizada por Admin, pero se mantienen como entidades separadas.

### Decisión clave
**El sistema debe dejar de utilizar cálculos volátiles para cotizaciones y pasar a utilizar `proposals` como fuente de verdad persistente.**

*El siguiente paso será **1B2.5.3 — Modelo técnico**, donde definiremos cómo adaptar el esquema actual y gestionar los estados sin romper la compatibilidad operativa.*

Resultado de 1B2.5.2
El diseño funcional queda definido como:
La Propuesta es la oferta formal derivada de una solicitud evaluada, presentada al autor para aceptación o rechazo, y la aceptación puede conducir a la creación/activación del proyecto según las reglas de negocio.

Y lo más importante: el flujo actual de “cotización” debe dejar de saltarse proposals.
El siguiente paso es 1B2.5.3 — Modelo técnico, donde vamos a decidir exactamente cómo usar project_requests, evaluations, proposals y projects sin duplicar estados ni romper lo que ya funciona.
