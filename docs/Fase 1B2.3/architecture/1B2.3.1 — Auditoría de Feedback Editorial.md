## Lectura de la matriz

### 1. Feedback editorial

Es la pieza más cercana a una funcionalidad editorial estructurada actualmente.

Existe una relación entre:

```text
Proyecto
   ↓
Deliverable
   ↓
Review / Feedback


Admin puede generar comentarios sobre entregables.
Sin embargo, el Dashboard del autor todavía no presenta esta capacidad como una sección editorial claramente diferenciada.
Estado: funcional en backend, pero experiencia incompleta en Dashboard.
2. Contacto / Soporte
Actualmente existen dos mecanismos principales:
SupportPanel
   ↓
Modal o mailto:

/contacto
   ↓
Formulario de contacto
Esto permite iniciar una solicitud de ayuda, pero no constituye todavía un sistema de conversaciones persistentes.
Estado: funcional como contacto, pero no como sistema de soporte conversacional.
3. Notificaciones
Existe una infraestructura real:
notifications
   ↓
notification.service.ts
   ↓
Navbar / campana
El sistema permite consultar notificaciones y gestionar su estado de lectura.
Sin embargo, la estructura actual es relativamente básica y no contiene todavía metadata avanzada para identificar claramente el tipo de evento o la entidad relacionada.
Estado: funcional, pero ampliable.
4. Timeline / actividad
Existe una tabla timeline relacionada con los proyectos.
Su función es registrar acontecimientos:
Proyecto
   ↓
Timeline
   ├── Evento 1
   ├── Evento 2
   └── Evento 3
No debe convertirse en sistema de mensajes.
Estado: funcional como historial de actividad.
5. Propuestas
Existe:
project_requests
       ↓
proposals
Admin puede trabajar con propuestas y el autor puede acceder a la información permitida por RLS.
Sin embargo, la interfaz todavía no presenta un flujo de propuesta completamente desarrollado y separado.
Estado: funcional en estructura/backend, parcialmente desarrollado en UI.
6. Notas internas
Existe:
projects
   ↓
internal_notes
Las políticas RLS restringen estas notas a Admin.
Por diseño, deben permanecer completamente separadas de:
mensajes;
soporte;
feedback visible al autor;
notificaciones.
Estado: funcional para uso interno de Admin.
7. Mensajes / conversaciones
Actualmente no existe una infraestructura dedicada de:
conversations
messages
Por lo tanto, no existe todavía un sistema real de comunicación persistente entre autor y Admin.
La comunicación está actualmente distribuida entre:
Notifications
Reviews
Support
Timeline
Internal Notes
Proposals
Esto confirma la necesidad de diseñar posteriormente una capa de Mensajes / Conversaciones independiente, sin reutilizar incorrectamente ninguna de estas entidades como sustituto de un sistema de chat.
Conclusión de la auditoría 1B2.3.1
La auditoría confirma que el proyecto ya posee varias piezas de comunicación y feedback, pero cada una tiene una responsabilidad diferente.
La arquitectura funcional debe conservar esta separación:
Feedback editorial
→ Observaciones estructuradas sobre el trabajo

Mensajes
→ Conversación entre autor y equipo

Soporte
→ Solicitudes de ayuda

Notificaciones
→ Avisos del sistema

Timeline
→ Historial de acontecimientos

Internal Notes
→ Información privada de Admin

Proposals
→ Propuestas comerciales/editoriales
No se deben fusionar estas entidades para solucionar las carencias de UI.
