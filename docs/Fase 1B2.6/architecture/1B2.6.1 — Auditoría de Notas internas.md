# Auditoría de 1B2.6 — Notas internas (Admin-only)

Esta auditoría mapea el estado actual de las notas internas, confirmando que la infraestructura base y la seguridad ya están definidas, pero el módulo carece de interfaz de usuario e integración en el flujo administrativo.

## 1. Qué existe realmente
La tabla `public.internal_notes` está definida en Supabase con:
- `id`, `project_id`, `note`, `author_id`, `created_at`.
- Relaciones correctas con `projects` y `authors`.
- **Estado de datos**: La tabla existe, pero está vacía (0 filas).

## 2. Seguridad (RLS)
- **RLS**: Se confirma la existencia de `internal_notes_admin_only` y `internal_notes_admin_delete` basadas en `is_admin()`.
- **Conclusión**: El diseño de seguridad es correcto: las notas son privadas para el Admin y no deben ser visibles para el Autor.

## 3. Matriz de Auditoría 1B2.6

| Funcionalidad | Existe | Funciona | Parcial | Descon. | Falta | Admin | Dash. | Supabase |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |

## 4. Discrepancias identificadas
- **Ausencia de experiencia**: La base de datos está preparada, pero no hay interfaz en `admin/page.tsx` para listar, crear o editar notas.
- **Servicios**: No existen hooks (`useInternalNotes`) ni un servicio específico en la arquitectura actual.

## 5. Conclusión operativa
El sistema tiene un excelente diseño base (seguridad y persistencia), pero es una capacidad "muerta". La prioridad de 1B2.6 no es alterar el modelo de datos, sino **integrar esta capacidad en la UI del Admin** dentro del contexto del proyecto, manteniendo siempre la privacidad respecto al autor.

## 6. Qué deja claro esta auditoría
`1B2.6` debe centrarse en **convertir la infraestructura técnica en una función útil**. No hace falta abrir el modelo ni cambiar RLS. El objetivo es que el Admin pueda gestionar notas privadas dentro del área de gestión de un proyecto específico, sin que esto se convierta en una herramienta de comunicación con el autor o una nota global del sistema.

├── author_id

internal_notes.author_id  → authors.id

2. Seguridad: esta parte sí está muy clara
Las RLS actuales son:
internal_notes_admin_only
con:
USING      is_admin()
WITH CHECK is_admin()
y además:
internal_notes_admin_delete
con is_admin().
Eso significa que internal_notes está diseñada explícitamente como información privada de Admin. No es una tabla accidentalmente abierta ni una versión escondida del sistema de mensajes. 
Esta parte de la arquitectura está bien encaminada.
3. Relaciones actuales
La cadena es:
projects
   ↓
internal_notes
   ↓
author_id opcional
El project_id es obligatorio.
Eso tiene una implicación importante:
Una nota interna siempre pertenece a un proyecto.

No es una nota global del sistema.
Eso encaja con el producto que estamos construyendo.

No aparece una sección dedicada de “Notas internas”.
Tampoco encontré en las búsquedas dirigidas un internal-notes service/component equivalente.
Por tanto:
internal_notes existe en backend, pero su experiencia de usuario todavía no está integrada como módulo real.
